# PRD: Tapir

> **Версія продукту:** 0.1.0  

## Програма для запису інтернет-радіо з повною доступністю для незрячих

---

## 1. Огляд продукту

### 1.1. Мета

Tapir — це спеціалізований десктопний додаток для Windows для запису музики з інтернет-радіостанцій з **повною доступністю для незрячих** (NVDA, JAWS, Narrator та ін.).

### 1.2. Проблема

Більшість програм для запису інтернет-радіо мають недостатню підтримку доступності для користувачів з вадами зору. Зрячому користувачу та сліпому доведеться витрачати різні зусилля, і останньому на кілька порядків складніше вирішити одну й ту саму потребу.

### 1.3. Цільова аудиторія

- Користувачі з вадами зору, що використовують скрінрідери
- Усі користувачі, які хочуть записувати інтернет-радіо на Windows
- Користувачі, яким потрібен портативний додаток (флешка, без інсталяції)

### 1.4. Ключові принципи

- **Доступність понад усе** — кожен елемент UI повинен бути доступний для скрінрідера
- **Портативність** — один EXE файл, без інсталятора, на будь-якій флешці
- **Простота** — мінімалістичний інтерфейс, зрозумілий без додаткового навчання

## 2. Платформа та розгортання

### 2.1. Цільова платформа

- **ОС:** Windows 11+ (тільки Windows)
- **Архітектура:** x64 (основна), x86 (опціонально)

### 2.2. Режим розповсюдження

- **Portable режим** — єдиний EXE файл
- Не потребує інсталяції
- Не потребує прав адміністратора
- Можна запускати з флешки або будь-якої теки
- Усі дані (налаштування, профілі, записи) зберігаються **поруч із EXE**
- **Автооновлення**: не передбачене (користувачі завантажують нову версію поверх EXE самостійно)

### 2.3. Структура файлів

```
Tapir/
├── tapir.exe                            # Головний виконуваний файл
└── data/                                # Усі дані додатку
    ├── settings.json                    # Глобальні налаштування програми (мова, тема, хоткеї, інше)
    ├── profiles/                        # Теки профілів
    │   ├── Default.tapirprofile            # Стандартний профіль за замовчуванням (JSON)
    │   └── My Profile.tapirprofile         # Додатковий користувацький профіль (JSON)
    ├── logs/                            # Файл журналу
    │   └── tapir.log
    └── recordings/                      # Записані файли (за замовчуванням)
        ├── Station Name/
        │   ├── Artist - Title.mp3
        │   └── ...
        └── ...
```

## 3. Вимоги до доступності (Accessibility)

### 3.1. Базові вимоги

- **Повна підтримка скрінрідерів:** NVDA, JAWS, Windows Narrator
- Використання нативних Windows Accessibility API (UI Automation / MSAA)
- Усі елементи інтерфейсу мають мати:
  - Accessible Name (назва)
  - Accessible Role (роль)
  - Accessible State (стан)
  - Accessible Description (опис, за потреби)
- Повна клавіатурна навігація (Tab, Shift+Tab, стрілки, Enter, Space, Escape)
- Логічний порядок фокусу (Tab Order)
- Видимий індикатор фокусу для клавіатурних елементів

### 3.2. Додаткові вимоги доступності

- **Оголошення про зміни:** зміна стану запису/відтворення, помилки з'єднання тощо
- **Live regions:** зміна назви треку, біт рейту, статусу підключення/відключення
- **Контраст та кольори:** мінімальний контраст за вимогами WCAG AA
- **Розміри шрифтів:** мінімальний розмір для читабельності (масштабування, збільшувальне скло)
- **Системний курсор:** підтримка великих курсорів Windows
- **Діалогові вікна:** фокусна пастка з послідовним фокусом
- **Помилки форми:** прив'язка до цільових полів для скрінрідерів
- **Деструктивні операції:** підтвердження або Undo для всіх дій, що неможливо скасувати

### 3.3. Стандарти доступності

- Microsoft Accessibility Guidelines для Windows-додатків
- Принципи WCAG 2.1 AA (contrast, labels, keyboard nav) — адаптовані для десктопного UI
- Повна підтримка UI Automation

## 4. Функціональні вимоги

### 4.1. Запис інтернет-радіо (Core)

#### 4.1.1. Підключення та запис потоків
- Повна підтримка ICY-протоколу (Icecast/SHOUTcast)
- Підтримка форматів: MP3 (Icecast/SHOUTcast), AAC
- ~~Підтримка HLS (HTTP Live Streaming, `.m3u8`)~~ — **поза scope v1** (HLS потребує складного парсингу playlist-файлів та послідовного downloader, що виходить за межі цієї версії)
- Відображення поточного статусу потоку (запис, зупинено, помилка, перепідключення)
- Автоматичне перепідключення при обриві з'єднання
  - Налаштування: максимальна кількість спроб (0 = нескінченно)
  - Налаштування: інтервал між спробами (секунди)
  - Експоненціальний backoff (зростає до максимально заданого інтервалу)

#### 4.1.2. Збереження записів на диск
- Збереження суцільного файлу (один файл на весь запис)
- Збереження окремих треків (за метаданими)
  - Опція `saveFirstTrack` (boolean): зберігати перший трек або ні. "Перший трек" — сегмент від моменту початку запису до першої зміни метаданих (частковий трек, запис розпочато посередині пісні).
    > **Canonical поле:** `skipFirstIncompleteTrack` (інвертована семантика: `saveFirstTrack: true` = `skipFirstIncompleteTrack: false`). Див. data-models.md.
    - `saveFirstTrack: true` — перший сегмент зберігається; якщо його тривалість < `minTrackDuration`, він все одно зберігається (виняток з правила мінімальної тривалості)
    - `saveFirstTrack: false` — перший сегмент завжди відкидається, незалежно від `minTrackDuration`
  - Опція `minTrackDuration` (мс): мінімальна тривалість треку для збереження (треки коротше за це значення відкидаються, окрім першого треку при `saveFirstTrack: true`)
    > **Canonical поле:** `skipShortTracksMs`. Псевдокод логіки — див. architecture.md §5.1.2.

#### 4.1.3. Обробка метаданих
- Автоматичне отримання метаданих із ICY metadata (artist, title) під час підключення до радіостанції (ICY metadata)
- Розбиття файлів за треками (автоматично): використовується зміна метаданих як сигнал для розділення

#### 4.1.4. Іменування файлів
- Гнучкий шаблон імені файлу за патерном:
  - `%a` — виконавець
  - `%t` — назва треку
  - `%l` — альбом
  - `%s` — назва станції
  - `%n` — номер треку
  - `%d` — дата
  - `%time` — час
- Різні шаблони для:
  - завершених записаних треків
  - незакінчених записів (суфікс `_incomplete`)
  - файлів потоку
- Налаштування: шлях для збереження
- Підтримка теки у шаблоні через `\` (напр. `%s\%a - %t`)
- **Санітизація**: заборонені у Windows символи (`\ / : * ? " < > |`) замінюються на `_`; краї рядків (пробіли/крапки) обрізаються
- **Колізії**: якщо файл з таким іменем вже існує, додається суфікс `_2`, `_3` тощо (без перезапису)
- **Кодування ICY**: очікуємо UTF-8, але fallback до latin-1 (ICY-протокол офіційно latin-1, але багато серверів надсилають UTF-8)

### 4.2. Відстеження треків (Wishlist)

#### 4.2.1. Список бажаних (Wishlist)
- Список бажаних треків/артистів для автоматичного запису
- Коли трек з потоку збігається з записом у wishlist, запис починається автоматично
- Підтримка wildcard-патернів: `*` (будь-які символи), `?` (один символ)
- Опція: зберігати тільки для конкретного потоку
- Опція: фільтр формату для автоматичного запису (MP3/AAC/будь-який)
- Опція: видалити з wishlist після запису
- Опція: додавати знайдений трек в ignorelist після запису

#### 4.2.2. Список ігнорованих (Ignorelist)
- Глобальний ignorelist — для всіх потоків
- Додатковий ignorelist — per-stream налаштування
- Автоматичне додавання записаних треків до ignorelist (опція)

#### 4.2.4. Порядок перевірки (Precedence)

При зміні ICY метаданих перевірка виконується в такому порядку:
1. Per-stream ignorelist → збіг → відкинути трек
2. Global ignorelist → збіг → відкинути трек
3. Wishlist → збіг → автоматичний запис
4. Жодного збігу → звичайна поведінка (запис якщо ручний запис активний)

**Ignorelist завжди має пріоритет над wishlist.** Якщо трек збігається з обома списками — він ігнорується.

#### 4.2.3. Списки (Lists)
- Wishlist (бажані) — автоматичний запис
- Ignorelist (ігноровані) — фільтр небажаного
- Імпорт/експорт у текстовий формат
- Експорт у m3u/pls плейлисти

### 4.3. Програвач (Player)

#### 4.3.1. Відтворення потоку
- Прослуховування потоку в реальному часі
- Одночасне відтворення і запис потоку
- Регулювання гучності
- Вибір аудіопристрою виведення

#### 4.3.2. Відтворення записаних файлів
- Відтворення записаних файлів MP3/AAC
- Повна навігація: перемотка, пауза, зупинка, поновлення
- Відображення прогресу

#### 4.3.3. Інформація про відтворення
- Живий потік: поточний трек і виконавець (ICY metadata)
- Файл: метадані (артист, назва, альбом, тривалість)
- Без окремого плейлиста керування: список збережених пісень не є чергою відтворення, не підтримує ручне перевпорядкування або автоматичну послідовність програвання
- Оголошення зміни треку (live region)

### 4.4. Заплановані записи (Scheduled Recordings)

#### 4.4.1. Параметри та налаштування розкладу
- Прив'язка до конкретного потоку з профілю
- Два типи:
  - **Одноразовий** — конкретна дата, час і тривалість запису
  - **Повторюваний** — вибирається день тижня, час і тривалість запису
- Параметри запису розкладу за типом:
  - **Одноразовий:** дата (YYYY-MM-DD), час початку (HH:MM), тривалість (хвилини)
  - **Повторюваний:** день тижня (число), час початку (HH:MM), тривалість (хвилини)
- Можливість увімк/вимк окремо (без необхідності видаляти)
- Текстовий опис запису для орієнтації (user label)

#### 4.4.2. Поведінка розкладу
- Автоматичний контроль за часом системи (час системи визначає коли записувати)
- **Часовий пояс**: використовується локальний час системи (без UTC-перетворення, оскільки Portable-додаток завжди працює на конкретній машині)
  - Перехід на літній час (spring-forward, пропущена година): запланований запис виконується у найближчий доступний час (напр. 02:30 → 03:30)
  - Перехід на зимовий час (fall-back, подвоєна година): запланований запис виконується лише один раз (при першому входженні у цей час)
- Якщо потік вже записується — запланований запис додатково не дублює потік
- Після завершення розкладу — автоматичне зупинення запису, якщо його запустив розклад

#### 4.4.3. Граничні та крайові ситуації

| Ситуація | Поведінка |
|----------|-----------|
| Потік вже записується вручну | Продовжується без змін; коли розклад спрацює — не створює другий запис |
| Час розкладу припадає на час, коли вже йде запис | Ігнорується (запис вже активний); розклад відзначається як виконаний |
| Програму було закрито під час запланованого запису | Пропущений запис фіксується; відображення у логі: `[ScheduledRecording] Missed: <name> at <time>` |
| Аварійне завершення програми під час запланованого запису | Незавершений файл зберігається з суфіксом `_incomplete`; розклад позначається як виконаний (без автоматичного повтору); лог: `[ScheduledRecording] Crashed during: <name> at <time>`. Визначення крашу: при graceful exit зберігається прапор `clean_shutdown=true` у `data/state.json`; якщо при запуску прапор відсутній або `false` — попередній сеанс завершився аварійно |
| Потік недоступний під час спроби розкладу | Використовується стандартна логіка перепідключення, як і при ручному пуску |
| Кілька запланованих записів на один час | Усі записи запускаються як звичайні паралельні (якщо мережа дозволяє), якщо вони стосуються різних потоків |

#### 4.4.4. Інтеграція з UI
- Заплановані записи відображаються у секції розкладу в Activity Bar (окремий розділ для управління розкладом)
- Початок запису: "Запланований запис розпочато: <назва потоку>" (assertive live region)
- Закінчення запису: "Запланований запис завершено: <назва потоку>"
- Усі елементи мають бути оснащені accessible labels

### 4.5. Браузер потоків (Stream Browser)

#### 4.5.1. Пошук станцій
- Пошук за назвою, URL, жанром
- Фільтрація за форматом (MP3/AAC)
- Фільтрація за мінімальним бітрейтом
- Додавання станцій до профілю (до обраних потоків для запису)
- Навігація результатами у секції обраних потоків

#### 4.5.2. Джерела каталогу станцій
- Інтеграція з Radio Browser API (radio-browser.info) — основне API
- Підтримка додавання потоків вручну за URL
- Підтримка URL-файлів: пряме посилання, m3u, pls, asx плейлисти
- HTTP Basic Auth для закритих потоків — опціонально. URL зберігається без креденшіалів (напр. `http://host/stream`), логін/пароль зберігаються окремо з DPAPI-шифруванням. Authorization-заголовок формується при підключенні, не персиститься. Усі логи та повідомлення помилок мають санітувати URL від креденшіалів
- HTTP Proxy (налаштування у параметрах) — опціонально

### 4.6. Збережені записані треки (Saved Songs)

- Список усіх записаних треків
- Сортування, фільтрація, пошук
- Операції: відтворення (wishlist), ігнорування (ignorelist)
- Контекстне меню:
  - Відтворити
  - Відкрити у теці
  - Додати/видалити з wishlist/ignorelist
  - Видалити/перейменувати файл
  - Перейменування
  - Копіювати назву
  - Копіювати у буфер обміну
  - Редагувати теги
- Масові дії / сортування

### 4.7. Теги (Tags)

- Запис ID3v2 тегів для MP3
- Запис тегів для AAC
- Поля: артист, назва, альбом, жанр, назва радіо
- Дані: використовуються отримані метадані (Artist - Title)
- Підтримка ручного редагування тегів у збережених файлах

### 4.9. Системна інтеграція

#### 4.9.1. Загальне
- Автозапуск з Windows (опціонально; через запис у `HKCU\Run`, для Portable програми цей параметр прив'язаний до поточного місцерозташування EXE)
- Зменшення до системного лотку
- Відновлення сесій, що записувалися при виході
- Відображення назви треку у заголовку вікна
- Сповіщення про зміну треку (popup)
- Системні хоткеї для керування коли вікно не у фокусі (глобальні гарячі клавіші)
- Дія при подвійному кліку на потоці (запис / відтворення)

#### 4.9.2. Обмеження смуги пропускання
- Ліміт пропускної здатності для потоків (кБ/с)
- Налаштування для одночасного запису

#### 4.9.3. Гарячі клавіші (Hotkeys)
- Глобальні гарячі клавіші (працюють навіть коли вікно не у фокусі)
- Налаштування для:
  - Старт/зупинка запису
  - Відтворення/пауза
  - Збільшити/зменшити гучність
  - Показати/приховати програму
  - Попередній/наступний трек

#### 4.9.4. Профілі

**Профіль** — ізольований набір даних, що містить індивідуальний набір радіостанцій, налаштування запису (наприклад: "Робочий", "Музика", "Нічний ефір"). Перемикання між профілями дозволяє per-profile зміну набору налаштувань та радіостанцій.

**Глобальні налаштування** (зберігаються у `data/settings.json`, спільні для всіх профілів):
- Мова інтерфейсу та тема оформлення
- Гарячі клавіші
- `minimizeToTray`, `showTrayNotifications`
- Межа вільного місця на диску (для зупинки запису)
- Ім'я активного профілю (`activeProfile`)

**Per-profile дані** (зберігаються у файлі `.tapirprofile`, унікальні для кожного профілю):
- Список потоків (`streams`) + per-stream ignorelist
- Wishlist та глобальний ignorelist
- Заплановані записи (`scheduledRecordings`)
- Налаштування запису (`defaultOutputDir`, `fileNameTemplate`, `incompleteFileNameTemplate`, `streamFileNameTemplate`, `skipShortTracksMs`)
- Налаштування постобробки
- Рівень гучності програвача (`playerSession.volume`)
- Список збережених треків (`savedTracks`)
- URL потоків, що записувалися при закритті програми (`activeRecordingUrls`)

**Створення та операції:**
- Програма за замовчуванням створює профіль `Default.tapirprofile` з базовими налаштуваннями; він завжди може бути змінений
- При зміні профілю оновлюється відповідний елемент у глобальних налаштуваннях (ім'я зберігають у `data/settings.json`)
- Кожний профіль — це файл `.tapirprofile` (JSON) з повним набором per-profile даних
- Експорт профілю у файл
- Імпортування профілю
- Видалення профілю (крім `Default`)

#### 4.9.5. Логування
- Запис подій у лог-файл (`data/logs/tapir.log`)
- Усі події записів та помилок мають маркер; у двопотоковому контексті кожен рядок: `[StationName] ...`
- Параметри: ротація, розмір, рівень деталізації
- Очистка логу (опціонально)

#### 4.9.6. Тема оформлення

- Підтримка світлої (Light) та темної (Dark) тем оформлення
- Автоматичне визначення системної теми Windows:
  - Зчитується поточна тема через `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize\AppsUseLightTheme`
  - При неможливості визначити — fallback на темну тему
- Налаштування теми зберігаються у `data/settings.json` з варіантами: `"auto"`, `"dark"`, `"light"`
- За замовчуванням — `"auto"` (слідувати за темою Windows)

### 4.11. Аргументи командного рядка

Реалізація через `tauri-plugin-cli` (clap-based). Підтримуються як короткі (`-r`), так і довгі (`--record`) форми.

#### 4.11.1. Список аргументів

| Короткий | Довгий | Значення | Опис |
|----------|--------|----------|------|
| `-d` | `--datadir` | `PATH` | Задати шлях до каталогу даних |
| `-t` | `--tempdir` | `PATH` | Задати шлях до тимчасових файлів |
| | `--profile` | `NAME` | Запустити з конкретним профілем замість стандартного |
| `-m` | `--minimize` | — | Запуск згорнутим до tray |
| `-r` | `--record` | `URL` | Почати запис потоку |
| `-p` | `--play` | `URL` | Почати програвання потоку |
| | `--stop-recording` | `[URL]` | Зупинити запис (конкретного URL або всіх, якщо URL не вказано) |
| | `--stop-playback` | — | Зупинити програвання |
| | `--wish-add` | `TITLE` | Додати до wishlist |
| | `--wish-remove` | `TITLE` | Видалити з wishlist |
| `-h` | `--help` | — | Показати довідку |
| `-V` | `--version` | — | Показати версію |

#### 4.11.2. Поведінка

- **Множинні аргументи:** допускається кілька `--record URL1 --record URL2` одночасно — кожен запускає окремий запис
- **Конфліктні аргументи:** `--record` і `--play` можна комбінувати (запис і програвання різних потоків)
- **Помилковий профіль:** якщо `--profile NAME` не знайдено — exit code 1, stderr: `Error: profile "NAME" not found`
- **Помилковий URL:** якщо URL нерозпізнаний або з'єднання неможливе — exit code 1, stderr: `Error: cannot connect to URL`

#### 4.11.3. Single-instance взаємодія

- При повторному запуску аргументи передаються першій інстанції через Named Pipe (via `tauri-plugin-single-instance`)
- Друга інстанція чекає відповідь (success/error) від першої, виводить результат у stdout/stderr та завершується
- Якщо Named Pipe недоступний (перша інстанція зависла або crash) — exit code 1, stderr: `Error: cannot communicate with running instance`
- Аргументи `--datadir`, `--tempdir`, `--profile`, `--minimize` ігноруються при передачі вже запущеній інстанції (працюють лише при першому запуску)

#### 4.11.4. Exit codes

| Код | Значення |
|-----|----------|
| `0` | Успіх |
| `1` | Помилка аргументів або виконання (профіль не знайдено, URL недоступний тощо) |
| `2` | Невалідні аргументи (невідомий прапорець, відсутнє обов'язкове значення) |

> Для Tauri IPC (не CLI) усі команди повертають `Result<T, String>`; помилка серіалізується у frontend як rejected invoke promise з текстом помилки.

#### 4.11.5. Вивід

- При CLI-операціях (`--record`, `--play`, `--wish-add` тощо): stdout повідомлення про результат (напр. `Recording started: URL`)
- При помилках: stderr з описом помилки
- При запуску GUI без CLI-аргументів: stdout/stderr не використовуються

### 4.12. Локалізація

- Підтримка двох мов: українська та англійська
- Мова визначається автоматично при першому запуску за системною локаллю Windows, та зберігається у файлі налаштувань (напр., `"language": "uk-UA"` або `"language": "en-US"`)
- Будь-коли мову можна змінити у налаштуваннях програми (`data/settings.json`)
- Якщо системна локаль не відповідає жодній із підтримуваних мов — fallback на англійську

## 5. Нефункціональні вимоги

### 5.1. Продуктивність

- Стабільний одночасний запис щонайменше 20+ потоків паралельно
- Мінімальне споживання RAM (< 200 МБ для 20 потоків)
- Мінімальне навантаження на CPU
- Швидкий запуск (< 3 секунди)

### 5.2. Надійність

- Автоматичне перепідключення при розриві
- Збереження файлів при аварійному завершенні
- Коректне відновлення записів після перезапуску
- Обробка помилок мережевих запитів
- Запис файлів (незавершені треки): зберігає з суфіксом `_incomplete`; не видаляються автоматично
- Одна інстанція (single-instance): повторний запуск програми передає аргументи першій інстанції (через Named Pipe) та завершується

### 5.3. Безпека

- Підтримка HTTPS/TLS потоків
- Безпечне зберігання паролів (шифрування через DPAPI на рівні системи)
- Усі ресурси додатку не передаються на зовнішні сервери; єдиний зовнішній запит — до Radio Browser API та серверів радіостанцій

### 5.4. Розмір

- Один EXE файл, ≤ 80 МБ (Tauri v2 + Rust з LTO та strip)
- Мінімум зовнішніх залежностей (ціль: zero dependencies)

### 5.5. Сумісність

- Windows 11 (build 22000+)
- Скрінрідери: NVDA 2023+, JAWS 2023+, Windows Narrator

## 6. Формат зберігання даних

### 6.1. Глобальні налаштування (`data/settings.json`)
- JSON формат, людиночитабельний (pretty-printed)
- Містить лише налаштування, що стосуються **усієї програми** незалежно від профілю:
  - Мова, тема, глобальні хоткеї, системні параметри, розмір логу, межа місця на диску
  - Ім'я активного профілю (`activeProfile`)

### 6.2. Профіль (`.tapirprofile`)
- JSON формат, людиночитабельний
- Зберігається у теці `data/profiles/`
- Кожний файл відповідає одному набору даних користувача
- Містить per-profile дані:
  - Список потоків та їх per-stream ignorelist
  - wishlist та глобальний ignorelist
  - Заплановані записи
  - Налаштування запису (шлях, шаблон, параметри)
  - Налаштування постобробки
  - Сесія програвача
  - Список збережених треків

### 6.3. Лог (`data/logs/tapir.log`)
- Текстовий файл
- Ротація логу (налаштовується)

## 7. Глосарій

| Термін | Визначення |
|--------|-----------|
| ICY Metadata | Протокол та метадані ICY (Icecast/SHOUTcast), що містять назву треку |
| Wishlist | Список бажаних треків/артистів для автоматичного запису |
| Ignorelist | Список треків, що мають ігноруватися (не записувати) |
| Portable | Додаток без потреби інсталяції, працює з будь-якої теки |
| Скрінрідер | Програма озвучення екрана для незрячих користувачів (NVDA, JAWS) |
| ID3 | Стандарт метаданих для MP3 файлів |
| Stream Browser | Каталог інтернет-радіостанцій з можливістю пошуку |
| Postprocessing | Автоматична зовнішня обробка файлів після завершення запису |
