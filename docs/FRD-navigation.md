# FRD: Зонна клавіатурна навігація та композиційні списки

> Статус: draft  
> Дата: 2026-04-23  
> Версія продукту: 0.1.0  
> Базовий стан репозиторію: Phase 3B завершено, активна гілка `feature/nav`

> **Оновлення (2026-05-27):** уточнено модель композиційних списків за результатами реалізації:
> 1. вертикальний рух (`Up` / `Down`, `Home` / `End`, `PageUp` / `PageDown`) завжди повертає фокус на summary цільового елемента (весь рядок); активний індекс сегмента **не** переноситься між рядками (раніше §7.3.3 вимагала збереження сегмента);
> 2. сегмент «дії» більше не є одним згрупованим фокус-стопом — кожна кнопка дії є окремим фокус-стопом (нативна `button`), досяжним через `Left` / `Right`;
> 3. при summary-фокусі весь рядок візуально виділяється.
> Модель спільна для всіх композиційних списків (Потоки, Браузер, Wishlist/Ignorelist).

> **Оновлення (2026-06-02):** консистентність верхніх зон і спрощення Command Palette:
> 1. **Два патерни внутрішньозонної навігації** зафіксовано як правило (див. §6.1.1): *composite-зона* однотипних простих контролів — стрілки + `Home`/`End`, `role="application"`; *form-зона* (текст, `Select`, `NumberField`) — нативний `Tab` між полями, `role="search"`/`group`. Обидва типи — **іменовані зони** з однаковим озвученням назви при вході.
> 2. **Кнопку Command Palette прибрано з усіх екранів.** Тимчасово єдиний спосіб відкриття — `Ctrl+K`. Це свідома проміжна відмова від вимог «кнопка досяжна через `Tab`» у §7.1.3, §7.4.2, §7.8.1 і критерії §10.3 (палітра наразі без discoverability для скрінрідера). Повернення discoverability — окреме майбутнє рішення.
> 3. Глобальні хоткеї `Ctrl+K` і `Ctrl+,` переведено на `event.code` (`KeyK`/`Comma`) — раніше `event.key === "k"` не спрацьовував на кириличній розкладці (порушення §6.5).
> 4. Назви зон вирівняно: браузерна form-зона — «Пошук і фільтри» (`role="search"`); тулбар Потоків — «Дії потоку».

## 1. Призначення

Цей документ описує функціональні вимоги до нової фічі: уніфікованої клавіатурної навігації по зонах застосунку та нового патерна списків без HTML-таблиць для екранів, де користувач працює з потоками, результатами пошуку, патернами, піснями та розкладом.

Фіча має забезпечити:

- передбачувану навігацію лише клавіатурою;
- повну придатність для NVDA як основного скрінрідера користувача;
- однакову ментальну модель на вже реалізованих і майбутніх екранах;
- відмову від табличної розмітки для списків потоків і подібних сутностей.

---

## 2. Контекст і поточний стан

На момент написання документа в репозиторії вже існують:

- головне вікно з `ActivityBar`, `ScreenHeader`/`ScreenZone`, основною панеллю, `PlayerPanel`, `StatusBar`;
- реалізовані екрани: Потоки, Браузер потоків, Wishlist/Ignorelist, Налаштування, Command Palette;
- ще не реалізовані, але вже заплановані екрани: Збережені пісні, Розклад;
- поточні списки на кількох екранах побудовані як `Table` з React Aria Components.

Ця фіча змінює саме модель взаємодії з UI. Вона не змінює бізнес-логіку запису, відтворення, пошуку, wishlist або scheduler.

Цей FRD є пріоритетним джерелом вимог для цієї фічі та замінює попередні припущення в документації, де списки описані як `table` або `grid` для таких екранів:

- Потоки;
- Браузер потоків;
- Wishlist / Ignorelist;
- Збережені пісні;
- Розклад.

---

## 3. Межі фічі

### 3.1. In scope

- циклічне переміщення фокуса між зонами головного вікна через `Tab` / `Shift+Tab` і сумісні швидкі переходи через `F6` / `Shift+F6`;
- зонна навігація всередині активного екрана;
- новий список потоків без HTML-таблиці;
- аналогічна модель для інших спискових екранів;
- доступність усіх переходів, станів і змін для NVDA;
- оновлені вимоги для модальних поверхонь: Command Palette, Settings, ConfirmDialog, Add/Edit dialogs.

### 3.2. Out of scope

- зміна глобальних гарячих клавіш у бекенді;
- зміна Tauri IPC контрактів, якщо вона не потрібна суто для навігації;
- переробка системного tray-меню;
- нові бізнес-функції запису, відтворення, scheduler, saved songs manager.

---

## 4. Зафіксовані продуктові рішення

Для цієї версії FRD зафіксовані такі рішення:

1. `StatusBar` входить у цикл `Tab` / `Shift+Tab` як окрема зона головного вікна.
2. Для списку потоків і аналогічних екранів заборонено використовувати як HTML-таблицю, так і ARIA `grid` / `treegrid`.
3. Кнопка відкриття Command Palette залишається частиною шапки основної панелі і не вводить окрему зовнішню зону в загальний цикл.
4. Для спискових зон використовується власний composite-патерн на базі нативного списку або семантики `list` / `listitem` з roving focus.
5. `listbox` також не використовується для багатоскладових рядків, бо він сплющує контент до одного озвучуваного рядка й не підходить для внутрішніх підчастин елемента.

---

## 5. Терміни

### 5.1. Зона

Логічна ділянка інтерфейсу, на якій фокус зупиняється при `Tab` / `Shift+Tab`.

### 5.2. Екранна зона

Зона всередині активного екрана основної панелі. Наприклад: панель дій, форма пошуку, список елементів.

### 5.3. Елемент списку

Одна сутність у списковій зоні: потік, станція, патерн, пісня або запис розкладу.

### 5.4. Сегмент елемента

Окрема складова елемента списку, по якій рухається фокус через `Left` / `Right`. Приклади: стан, назва, технічна інформація, дії.

### 5.5. Summary-фокус

Початковий фокус на елементі списку, коли скрінрідер озвучує короткий підсумок елемента цілком, а не окремий сегмент.

## 6. Глобальна модель навігації

### 6.1. Загальні принципи

- У головному вікні `Tab` і `Shift+Tab` рухають фокус між зонами, а не між кожним окремим контролом застосунку.
- Усередині зони навігація виконується переважно стрілками, `Home`, `End`, `PageUp`, `PageDown`.
- Якщо конкретний нативний контрол має власну усталену модель клавіш, його рідна поведінка має пріоритет. Це стосується, зокрема:
  - текстових полів;
  - `Slider`;
  - `NumberField` / spinbutton;
  - `Select` / popover;
  - `Tabs`;
  - `ComboBox`.
- У фокусі завжди має бути реальний елемент DOM з видимим focus indicator.
- Фокус ніколи не повинен губитися на `body` або на прихованому вузлі після видалення елемента, закриття діалогу чи зміни секції.
- DOM order, візуальний порядок і порядок озвучення скрінрідером мають залишатися узгодженими.
- Заборонено використовувати позитивні значення `tabindex`.

### 6.1.1. Два патерни навігації всередині зони

Усередині зони використовується один із двох патернів — залежно від вмісту. Обидва однаково є **іменованими зонами** (контейнер має доступну назву й озвучується при вході); відрізняється лише клавіша переходу між елементами:

| Тип зони | Вміст | Перехід між елементами | Роль контейнера |
| --- | --- | --- | --- |
| **Composite (toolbar-подібна)** | однотипні прості контроли: кнопки, чипи, елементи списку | `Left`/`Right` (або `Up`/`Down`) + `Home`/`End`, roving focus | `role="application"` |
| **Form** | змішані нативні віджети: текст, `Select`, `ComboBox`, `NumberField` | нативний `Tab` між полями; всередині віджета — рідні клавіші | `role="search"` або `role="group"` |

`Tab` / `Shift+Tab` (і `F6`) завжди виходять до сусідньої зони — однаково для обох типів. Form-патерн обрано там, де контроли мають власну усталену клавіатурну модель (§6.1), бо стрілкова навігація конфліктувала б із нею (текстова каретка, зміна вибору в `Select`, інкремент `NumberField`). Приклади: зона дій Потоків/Профілів — composite; зона пошуку та фільтрів Браузера — form.

### 6.2. Цикл зон головного вікна

Базовий цикл зон для головного вікна:

`ActivityBar → зони активного екрана в Main → Player → StatusBar → ActivityBar`

### 6.2.1. Правила циклу

- `Tab` рухається вперед по циклу.
- `Shift+Tab` рухається назад по циклу.
- `F6` і `Shift+F6` повинні виконувати той самий міжзонний перехід як desktop-friendly alias-и; їхня поведінка не може розходитись із `Tab` / `Shift+Tab`.
- Цикл зациклений.
- Якщо певна зона тимчасово не змонтована, вона пропускається.
- Якщо зона змонтована, але не містить доступних дій, вона все одно може лишатися в циклі, якщо несе важливу інформацію для користувача. Це правило стосується `StatusBar`.

### 6.3. Пам'ять фокуса

- Кожна зона запам'ятовує останній сфокусований підконтекст.
- Для спискової зони запам'ятовується:
  - ID останнього активного елемента;
  - активний сегмент усередині елемента;
  - позиція скролу, якщо це не суперечить поточному фільтру або сортуванню.
- Якщо запам'ятований елемент більше не існує, фокус переходить на найближчий доступний сусідній елемент, а якщо таких немає, на перший елемент зони.

### 6.4. Озвучення зміни зони

При вході в нову зону має виконуватися коротке `aria-live="polite"`-оголошення назви зони, якщо назва зони не була достатньо явно озвучена самим фокусом.

Приклади:

- «Бокова панель»;
- «Дії потоку»;
- «Список потоків»;
- «Програвач»;
- «Статус».

Оголошення не повинні дублювати текст, який NVDA щойно вже прочитав самостійно.

### 6.5. Клавіатурні обробники

Кастомні клавіатурні обробники для семантичних клавіш навігації мають спиратися на `event.key`, а `event.code` слід використовувати лише там, де важлива саме фізична клавіша незалежно від розкладки. Типові приклади для `event.code`: захоплення хоткея в `KeyRecorder`, desktop-сумісні low-level shortcut-обробники або сценарії, де потрібна конкретна фізична клавіша, а не символ.

## 7. Вимоги до зон і екранів

### 7.1. Головне вікно

### 7.1.1. Обов'язкові зони

У головному вікні завжди мають існувати такі верхньорівневі зони:

- `ActivityBar`;
- одна або більше зон активного екрана в `Main`;
- `Player`;
- `StatusBar`.

### 7.1.2. Внутрішні зони `Main`

Активний екран у `Main` може додавати власні зони. Ці зони вставляються в глобальний цикл між `ActivityBar` і `Player`.

### 7.1.3. Шапка секції

- Заголовок секції не є окремою зоною сам по собі.
- Якщо у шапці секції є інтерактивні елементи, вони входять до першої зони активного екрана.
- Command Palette відкривається лише `Ctrl+K` (див. §7.8.1); окремої кнопки-тригера в шапці немає.

### 7.2. ActivityBar

### 7.2.1. Семантика

- `ActivityBar` лишається навігаційною зоною застосунку.
- Рекомендована семантика контейнера: `nav` з чіткою міткою.

### 7.2.2. Клавіші

- `Up` / `Down`: перехід між елементами навігації;
- `Home` / `End`: перший / останній елемент;
- `Enter` / `Space`: активація секції або кнопки;
- `Tab` / `Shift+Tab`: вихід із зони до наступної / попередньої зони.

### 7.2.3. Disabled-елементи

- Майбутні секції, які ще не реалізовані, мають бути discoverable усередині `ActivityBar`.
- Такі елементи дозволено залишати доступними для стрілкової навігації в межах зони, але вони не повинні активуватися.
- Якщо disabled-елемент має лишатися discoverable у стрілковій навігації, він не може бути нативно `disabled`, якщо це прибирає його з roving focus; слід використовувати `aria-disabled="true"` або еквівалентну неактивну семантику.
- NVDA має озвучувати, що секція недоступна, а також коротке пояснення, якщо воно є.

### 7.2.4. Склад елементів

У зону входять:

- секції застосунку;
- кнопка налаштувань;
- майбутній profile switcher, коли він буде реалізований.

### 7.3. Екран «Потоки»

### 7.3.1. Зони екрана

Екран «Потоки» має формувати щонайменше дві зони:

1. зона дій екрана;
2. зона списку потоків.

### 7.3.2. Зона дій екрана

До цієї зони входять:

- кнопка додавання потоку;
- кнопка зупинки всіх записів;
- фільтр-чипи стану (Усі / Записуються / З помилками);
- майбутні фільтри чи допоміжні кнопки, якщо вони з'являться.

Правила:

- якщо елементи візуально утворюють групу з трьох і більше контролів, зона має поводитися як toolbar-подібна група;
- `Left` / `Right` переміщують фокус між контролами цієї зони;
- `Home` / `End` переходять на перший / останній контрол;
- `Tab` / `Shift+Tab` виходять до сусідньої зони.

### 7.3.3. Зона списку потоків

#### Загальні вимоги

- Список потоків не може бути HTML-таблицею.
- Список потоків не може використовувати ARIA `grid`, `treegrid` або `listbox`.
- Базова семантика має бути побудована на нативному списку (`ul` / `li`) або еквіваленті `role="list"` / `role="listitem"`.
- Навігація всередині списку реалізується через roving focus.

#### Модель елемента потоку

Кожен елемент потоку повинен мати:

- summary-фокус;
- впорядкований набір сегментів;
- стабільний ID для відновлення фокуса;
- accessible name для summary-фокуса;
- доступні назви для кожного сегмента.

Мінімальний набір сегментів:

1. summary: стан потоку + назва потоку (фокусує весь рядок);
2. поточний трек;
3. технічна інформація;
4. статус відтворення / запису / тривалість, якщо релевантно;
5. дії — **кожна** дія (кнопка) є окремим фокус-стопом, а не одним згрупованим сегментом «дії». Кнопки — нативні `button`, що активуються Enter/Space/кліком; навігація між ними така сама, як між сегментами (`Left` / `Right`).

#### Клавіші в списку потоків

- `Up` / `Down`: перехід до попереднього / наступного потоку;
- `Home` / `End`: перший / останній потік;
- `PageUp` / `PageDown`: перехід на приблизно один візуальний екран списку вгору / вниз;
- `Left` / `Right`: перехід між сегментами та кнопками дій активного потоку;
- `Enter`: на summary — основна дія потоку (toggle запису); на кнопці дії — її нативна активація;
- `Space`: на summary або інфо-сегменті — toggle (запис); на кнопці дії — нативна активація кнопки;
- `Delete`: видалити потік з підтвердженням (працює і коли фокус на кнопці дії);
- `Shift+F10` або `ContextMenu`: відкрити контекстне меню потоку;
- `Tab` / `Shift+Tab`: вихід до наступної / попередньої зони.

#### Правила сегментної навігації

- При першому вході в список фокус потрапляє на summary останнього активного потоку або на перший потік.
- `Right` переводить фокус із summary на перший сегмент, далі на наступні сегменти й кнопки дій.
- `Left` рухає у зворотному порядку, аж до summary.
- `Up` / `Down` (а також `Home` / `End`, `PageUp` / `PageDown`) **завжди** повертають фокус на summary цільового елемента — на весь рядок. Активний індекс сегмента **не** переноситься між рядками: після заходу в сегмент чи на кнопку повторне `Up` / `Down` знову виділяє цілий рядок сусіднього елемента.
- При summary-фокусі весь рядок елемента візуально виділяється (outline/рамка на рядку), видима в normal mode, light theme і Windows High Contrast.
- Ця модель сегментної навігації спільна для всіх композиційних списків (Потоки, Браузер потоків, Wishlist/Ignorelist).

#### Озвучення потоку

При summary-фокусі NVDA має почути щонайменше:

- стан запису;
- стан відтворення, якщо потік зараз відтворюється;
- назву потоку.

Елемент-рядок реалізовано як `listitem` (сам `<li>` є summary-фокусом) з `aria-roledescription` («потік» / «станція» / «патерн»), тому NVDA додає тип елемента замість загального «елемент списку». Не можна давати `aria-label` бездомному (`role`-less) `<div>`: Chromium експонує його як «section», і NVDA читає зайве «розділ».

Приклади summary-озвучення:

- «Записується, Radio Paradise, потік»;
- «Відтворюється, Jazz24, потік»;
- «Відтворюється, записується, SomaFM Groove Salad, потік».

При переході між сегментами має озвучуватися саме зміст активного сегмента, наприклад:

- «Трек, Tycho — A Walk»;
- «Бітрейт, 256 кбіт/с»;
- на кнопках дій озвучується кожна кнопка окремо: «Відтворити», «Записати», «Меню потоку».

#### Empty state

- Якщо потоків немає, замість списку показується empty state.
- У такому стані перший `Tab` у `Main` має приводити фокус на головну CTA-кнопку додавання потоку.
- NVDA має почути коротке пояснення, що список порожній і треба додати перший потік.

### 7.4. Екран «Браузер потоків»

### 7.4.1. Зони екрана

Екран «Браузер потоків» має формувати щонайменше дві зони:

1. зона пошуку та фільтрів;
2. зона результатів пошуку.

### 7.4.2. Зона пошуку та фільтрів

- Це form-зона (див. §6.1.1): `role="search"` з назвою «Пошук і фільтри», озвучуваною при вході.
- Усередині цієї зони використовується нативний порядок `Tab` між полями й контролами, оскільки тут переважають стандартні form widgets.
- Для `Select`, `ComboBox`, `NumberField`, `Input` діють їхні нативні правила клавіатури.
- Тригер Command Palette у цій зоні відсутній (див. оновлення 2026-06-02); палітра відкривається лише `Ctrl+K`.

### 7.4.3. Зона результатів пошуку

- Результати пошуку не можуть бути таблицею або grid.
- Патерн списку має бути тим самим, що й для потоків: список + елементи + сегменти + roving focus.

Мінімальні сегменти результату:

1. summary: назва станції (фокусує весь рядок);
2. метадані: країна, кодек, бітрейт, популярність;
3. дії: кнопка «Додати станцію» як окремий фокус-стоп (нативна кнопка), плюс контекстна дія, якщо буде додана.

Клавіші:

- `Up` / `Down`, `Home`, `End`, `PageUp`, `PageDown` між результатами (завжди на summary);
- `Left` / `Right` між сегментами та кнопкою дії;
- `Enter` на summary або на кнопці «Додати» додає станцію (кнопка активується нативно);
- після додавання фокус лишається на тому самому результаті.

### 7.4.4. Озвучення результатів

- При summary-фокусі озвучується назва станції.
- При переході на сегмент метаданих озвучується коротка технічна довідка.
- Після виконання дії має бути окреме `polite`-оголошення «Станцію додано: {name}».

### 7.5. Екран «Wishlist / Ignorelist»

### 7.5.1. Зони екрана

Екран має формувати щонайменше дві зони:

1. зона перемикання списку й дій;
2. зона активного списку.

### 7.5.2. Зона перемикання списку й дій

До зони входять:

- перемикач Wishlist / Ignorelist;
- кнопка додавання;
- кнопки імпорту / експорту, якщо вони присутні;
- інші дії поточного списку.

Правила:

- якщо використовується `Tabs`, `Left` / `Right` перемикають вкладки;
- кнопки після tablist мають бути досяжні звичайним `Tab` у межах цієї form/action-зони;
- перехід до зони списку виконується наступним `Tab`.

### 7.5.3. Зона списку патернів

- Wishlist і Ignorelist не можуть відображатися як table або grid.
- Кожен патерн є окремим елементом списку.

Мінімальні сегменти елемента:

1. summary: сам патерн (фокусує весь рядок);
2. умови: формат, мінімальний бітрейт, опції;
3. дії: кнопки «Редагувати» і «Видалити», кожна — окремий фокус-стоп (нативні кнопки).

Клавіші:

- `Up` / `Down`, `Home`, `End`, `PageUp`, `PageDown` між патернами (завжди на summary);
- `Left` / `Right` між сегментами та кнопками дій;
- `Enter` / `Space` на summary редагує патерн; на кнопці дії — її нативна активація;
- `Delete` відкриває підтвердження видалення.

### 7.5.4. Empty states

- Для порожнього Wishlist має бути фокусована CTA-кнопка додавання.
- Для порожнього Ignorelist має бути озвучуване повідомлення про порожній список і доступна дія додавання, якщо така передбачена дизайном.

### 7.6. Player

### 7.6.1. Місце в циклі зон

- `Player` завжди стоїть після зон активного екрана і перед `StatusBar`.

### 7.6.2. Внутрішня модель

`Player` є змішаною зоною:

- transport controls поводяться як компактна toolbar-група;
- `Slider` для позиції та гучності зберігають нативну поведінку.

### 7.6.3. Мінімальний порядок фокуса всередині Player

1. transport controls;
2. позиція відтворення, якщо є seekable source;
3. гучність.

### 7.6.4. Клавіші

- У transport controls: `Left` / `Right`, `Home`, `End` між кнопками;
- На `Slider`: нативні `Left` / `Right`, `PageUp` / `PageDown`, `Home`, `End`;
- `Tab` після останнього доступного контролу Player переходить у `StatusBar`.

### 7.6.5. Озвучення

- Поточне джерело відтворення має бути озвучуване без дублювання;
- зміна стану `play`, `pause`, `stop` має лишитися в live announcements;
- disabled-контроли не повинні руйнувати порядок навігації.

### 7.7. StatusBar

### 7.7.1. Обов'язкова зона

`StatusBar` входить у глобальний цикл зон і є останньою зоною перед поверненням у `ActivityBar`.

### 7.7.2. Вміст

Мінімально зона має підтримувати навігацію між такими сегментами статусу, якщо вони присутні:

1. кількість активних записів;
2. вільне місце на диску;
3. тривалість найдовшого запису;
4. інші майбутні статусні показники, наприклад пропускна здатність або активний профіль.

Якщо жоден статусний сегмент не є окремою фокусованою точкою, зона все одно повинна мати єдиний focus anchor: контейнер `StatusBar` або окремий summary-елемент із зрозумілою accessible name та видимим focus indicator.

### 7.7.3. Клавіші

- `Left` / `Right`: перехід між статусними сегментами, якщо в зоні їх більше одного;
- `Home` / `End`: перший / останній сегмент;
- `Tab`: повернення до `ActivityBar`;
- `Shift+Tab`: повернення до `Player`.

### 7.7.4. Озвучення

- Кожен сегмент має мати власну зрозумілу accessible name;
- read-only статус має бути придатним до читання з клавіатури, навіть якщо не має дії;
- якщо в майбутньому сегмент стане інтерактивним, його роль і текст мають лишитися зрозумілими без зміни місця в порядку зон.

### 7.8. Command Palette

### 7.8.1. Тригер

- **Тимчасово (з 2026-06-02): кнопки відкриття Command Palette немає на жодному екрані.** Єдиний спосіб відкриття — `Ctrl+K` (реалізовано через `event.code === "KeyK"`, тож працює незалежно від розкладки).
- Раніша вимога «кнопка досяжна через `Tab` у складі першої зони» призупинена до окремого рішення про повернення discoverability для скрінрідера.

### 7.8.2. Палiтра як overlay

Після відкриття Command Palette стає окремою модальною поверхнею і тимчасово зупиняє глобальний цикл зон головного вікна.

### 7.8.3. Структура

- поле пошуку / combobox input;
- список результатів;
- порожній стан або стан без результатів.

### 7.8.4. Клавіші

- `Escape`: закрити палітру і повернути фокус на тригер або елемент, який її відкрив;
- `Up` / `Down`: перехід між результатами;
- `Home` / `End`: перший / останній результат;
- `PageUp` / `PageDown`: швидкий перехід по довгому списку;
- `Enter`: виконати команду;
- `Tab` / `Shift+Tab`: працюють у межах стандартного фокусного порядку модального діалогу, але не повинні бути єдиним способом навігації по результатах; навігація списком лишається на `Up` / `Down`.

### 7.9. SettingsDialog

### 7.9.1. Загальне правило

`SettingsDialog` не використовує глобальний зонний цикл головного вікна. Це окремий модальний контекст із focus trap і стандартною послідовною `Tab`-навігацією.

### 7.9.2. Внутрішня структура

Всередині `SettingsDialog` мають бути доступні:

- вкладки категорій налаштувань;
- контент активної вкладки;
- кнопка закриття;
- усі поля форми в логічному порядку.

### 7.9.3. Клавіші

- `Tab` / `Shift+Tab`: стандартний рух по елементах діалогу;
- `Left` / `Right` у tablist: перемикання вкладок;
- `Escape`: закриття діалогу з поверненням фокуса у місце виклику;
- `Enter`: активує сфокусований контрол за його нативними правилами; цей FRD не вводить окрему модель «підтвердити і зберегти» для `SettingsDialog`.

### 7.9.4. Спеціальні вимоги

- KeyRecorder лишається окремим спеціальним контролом із власною моделлю захоплення клавіш;
- усі поля повинні мати явні мітки й повідомлення про помилки;
- ніякі елементи головного вікна не повинні бути доступні у фокусі, поки відкритий діалог.

### 7.10. Діалоги додавання, редагування і підтвердження

- `AddStreamDialog`, `AddPatternDialog`, `ConfirmDialog` використовують focus trap;
- всередині них діє стандартна послідовна `Tab`-навігація;
- `Escape` закриває діалог, якщо це безпечно;
- після закриття фокус повертається на елемент-викликач;
- у `ConfirmDialog` безпечна дія `Скасувати` має лишатися фокусом за замовчуванням.

### 7.11. Майбутній екран «Збережені пісні»

### 7.11.1. Зони екрана

Екран має формувати щонайменше дві зони:

1. зона фільтрів і дій;
2. зона списку пісень.

### 7.11.2. Зона фільтрів і дій

- form-подібна зона;
- стандартний `Tab` між `SearchField`, `Select`, кнопками дій;
- тригер Command Palette повинен бути досяжний у цій першій зоні, якщо він присутній у шапці.

### 7.11.3. Зона списку пісень

Список пісень використовує той самий композиційний патерн, що й список потоків.

Мінімальні сегменти:

1. summary: артист + назва + стан завершеності;
2. метадані: станція, тривалість, розмір, дата;
3. дії: відтворити, редагувати теги, показати файл, видалити.

Клавіші:

- `Up` / `Down`, `Home`, `End`, `PageUp`, `PageDown` між піснями;
- `Left` / `Right` між сегментами;
- `Enter` / `Space` на action-сегменті запускає дію;
- `Delete` або окрема дія видалення з підтвердженням;
- `F2` дозволено зарезервувати для редагування тегів або перейменування, якщо ця поведінка буде затверджена окремо.

### 7.12. Майбутній екран «Розклад»

### 7.12.1. Зони екрана

Екран має формувати щонайменше дві зони:

1. зона дій;
2. зона списку записів розкладу.

### 7.12.2. Зона дій

- кнопка створення запису;
- можливі фільтри або перемикачі стану;
- тригер Command Palette, якщо він присутній у шапці.

### 7.12.3. Зона списку розкладу

Список розкладу не використовує table або grid.

Мінімальні сегменти:

1. summary: назва запису + потік;
2. часові параметри: тип, день, час, тривалість;
3. стан: увімкнено / вимкнено / виконується;
4. дії: редагувати, увімкнути або вимкнути, видалити.

Клавіші:

- `Up` / `Down`, `Home`, `End`, `PageUp`, `PageDown` між записами;
- `Left` / `Right` між сегментами;
- `Space` на toggle-сегменті змінює enabled state;
- `Enter` на action-сегменті відкриває редагування.

### 7.12.4. Діалог створення / редагування

- окремий модальний контекст;
- стандартний `Tab`-порядок між полями;
- радіо-групи, date/time fields, selects і number fields лишають власну нативну модель клавіатури.

## 8. Вимоги до доступності

### 8.1. Підтримка скрінрідерів

Мінімальна обов'язкова підтримка:

- NVDA 2023+ на Windows;
- JAWS 2023+;
- Windows Narrator.

Рішення приймаються насамперед за якістю досвіду в NVDA.

### 8.2. Accessible name і state

- Кожна фокусована точка повинна мати зрозумілу accessible name.
- Якщо фокус стоїть на сегменті, його назва повинна містити або роль, або контекст сегмента.
- Стан запису, відтворення, помилки, disabled-state і toggle-state мають бути озвучуваними.

### 8.3. Видимий фокус

- Focus indicator має бути видимим у звичайній темі, light theme і Windows High Contrast.
- Не можна покладатися лише на зміну кольору фону без чіткої рамки, outline або іншого системно видимого індикатора.

### 8.4. Live announcements

Live announcements потрібні для:

- зміни стану запису;
- зміни стану відтворення;
- помилок;
- успішного додавання / видалення / збереження;
- переходу на сегмент, якщо сам фокус не дає достатнього озвучення.

Live regions не повинні дублювати нативне озвучення фокусованого елемента.

### 8.5. Вимоги до фокусу після дій

- після видалення елемента фокус переходить на сусідній елемент того самого списку;
- після закриття модального вікна фокус повертається туди, звідки користувач його відкрив;
- після зміни секції фокус переходить на першу доступну зону нового екрана;
- після виконання дії над елементом фокус за можливості лишається в тій самій зоні та на тому самому елементі.

## 9. Нефункціональні вимоги

- Модель навігації має бути консистентною на всіх екранах.
- У довгих списках навігація не повинна спричиняти відчутної затримки при переході між елементами.
- Зміни не повинні ламати portable-режим, Tauri window state або глобальні хоткеї.
- Реалізація не повинна залежати від миші для виявлення дій, сегментів або контекстного меню.
- Стан списку і фокуса має лишатися стабільним при оновленні даних у реальному часі, якщо активний елемент не видалений.

## 10. Критерії приймання

Фіча вважається завершеною, якщо виконані всі умови нижче.

### 10.1. Глобальна навігація

- `Tab` / `Shift+Tab` циклічно проходять `ActivityBar`, зони активного екрана, `Player`, `StatusBar`, а `F6` / `Shift+F6` дублюють той самий цикл.
- На кожному підтримуваному екрані зони проходяться в стабільному й передбачуваному порядку.
- Фокус не губиться після зміни секції, закриття діалогу або видалення елемента.

### 10.2. Списки

- Список потоків більше не рендериться як HTML-таблиця або ARIA `grid`.
- Аналогічно без table/grid рендеряться Browser results і Wishlist/Ignorelist.
- Для Saved Songs і Schedule цей самий критерій є обов'язковим у момент їхньої окремої реалізації, але не блокує приймання поточної фічі до появи самих екранів.
- `Up` / `Down`, `Home`, `End`, `PageUp`, `PageDown`, `Left`, `Right` працюють відповідно до цього FRD.
- NVDA озвучує summary потоку і його сегменти без втрати контексту.

### 10.3. Command Palette

- `Ctrl+K` відкриває палітру незалежно від розкладки клавіатури (`event.code`).
- *(Призупинено з 2026-06-02)* Кнопка відкриття, досяжна через `Tab`, тимчасово відсутня — див. §7.8.1.
- Після закриття палітри фокус повертається у попередній контекст.

### 10.4. Діалоги

- Усі модальні вікна мають focus trap.
- `Escape` працює послідовно там, де це безпечно.
- `ConfirmDialog` за замовчуванням фокусує безпечну дію.

### 10.5. Доступність

- Перевірка на NVDA підтверджує повну керованість без миші.
- Видимий фокус зберігається в normal mode і High Contrast.
- Немає дубльованих announcement-повідомлень при переході між елементами списку.

## 11. Наслідки для поточної реалізації

Після прийняття цього FRD очікуються такі зміни в коді й супровідній документації:

- `StreamTable`, `StationTable`, `PatternTable` мають бути замінені на нові спискові компоненти;
- `StreamRow` та аналогічні рядки мають стати списковими елементами із сегментною навігацією;
- `docs/accessibility.md`, `docs/architecture.md` і `docs/implementation-phases.md` потрібно буде оновити після імплементації, щоб прибрати старі table/grid-припущення й синхронізувати модель зонної навігації;
- тестові чеклісти ручного тестування потрібно буде доповнити сценаріями зонної навігації.

## 12. Джерела best practices

- [WAI-ARIA APG: Developing a Keyboard Interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/) — загальні правила фокуса, composite widgets, roving focus.
- [WAI-ARIA APG: Toolbar Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/) — клавіатурна модель для груп керування.
- [WAI-ARIA APG: Grid Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/grid/) — використано лише як аргумент, чому grid-патерн тут свідомо не обрано.
- [WAI-ARIA APG: Listbox Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/) — використано як аргумент, чому listbox не підходить для багатоскладових елементів із внутрішніми сегментами.
