# Скрінрідер мовчить на старті: вікно має бути foreground до ініціалізації webview

> Інженерна нотатка (учений урок). Tauri v2 + WebView2 + NVDA на Windows.
> Дата: 2026-05-30. Застосовно й до Electron / будь-якого Chromium-embedded десктопа.

## Коротко (TL;DR)

Якщо десктопний застосунок на вебв'ю стартує з **прихованим** вікном і показує його **з JS після завантаження даних**, скрінрідер (NVDA) часто **мовчить на старті** — невідтворювано, «приблизно кожен 5-й запуск працює».

**Причина:** скрінрідер приєднується до документа Chromium у момент його ініціалізації. Якщо тоді вікно ще не є OS-foreground, він чіпляється до **фонового** документа і вже **не озвучує фокус** до кінця сесії.

**Рішення:** показуй і фокусуй вікно **якомога раніше з нативного боку** (Rust `setup()` / main process), **до** того, як завантажиться вміст вебв'ю — поки ще діє Windows foreground-activation grant від запуску.

---

## Симптоми

- Візуально застосунок працює бездоганно: вікно з'явилося, фокус видно, миша/клавіатура працюють.
- NVDA **мовчить** одразу після старту: не озвучує сфокусований елемент, немає ознак переходу між browse mode і focus mode.
- Поведінка **невідтворювана**: інколи (рідко) озвучує нормально.
- Часто навіть подальша навігація в межах цієї сесії не озвучується.

Невідтворюваність — це майже завжди ознака **гонки** (race condition), а не логічної помилки.

## Корінь проблеми

1. Вікно конфігурується прихованим (Tauri `"visible": false`), щоб не блимати порожнім UI / щоб встигла застосуватись збережена позиція вікна.
2. Фронтенд робить `await` кількох IPC-викликів (завантаження даних), і лише потім викликає `window.show()` + `setFocus()` — це ~100+ мс після старту.
3. Тим часом вебв'ю (Chromium) **вантажиться паралельно**. NVDA приєднується до його документа.
4. Windows видає процесу право вивести вікно на передній план (**foreground-activation grant**) лише на короткий час після дії користувача (запуск). За ~100+ мс воно часто **згорає** → пізній `SetForegroundWindow` (через `show()`/`setFocus()`) Windows **ігнорує**: вікно з'являється, але не є справжнім foreground.
5. NVDA, що приєднався до **фонового** документа, не налаштовує підписку на події фокусу як слід → **тиша**, незалежно від того, коли й куди ми згодом ставимо DOM-фокус.

> Ключове: лагодити треба **момент показу вікна**, а **не** таймінг DOM-фокусу. Пізніше встановлення фокусу не допомагає — перевірено.

## Як діагностувати (швидко й однозначно)

Додай тимчасове логування у файл (Tauri: `tauri-plugin-log`) і зафіксуй для кожного запуску:

- `document.hasFocus()` на момент ініціалізації скрипта вебв'ю (найраніша точка);
- події `window` `focus`/`blur`, `document` `focusin`;
- `getCurrentWindow().onFocusChanged(...)` (OS-рівень foreground).

Потім зроби ~8–10 запусків, щоразу нотуючи «озвучив / мовчав», і зістав із логом. Очікувана **100% кореляція**:

| `document.hasFocus()` на старті webview | NVDA |
|---|---|
| `true` | 🔊 озвучує |
| `false` | 🔇 мовчить |

Якщо кореляція така — діагноз підтверджено: вікно не foreground у момент приєднання скрінрідера.

## Рішення

Показати + сфокусувати вікно з нативного боку, на старті, до завантаження вмісту вебв'ю.

**Tauri v2 (Rust, `lib.rs`):**

```rust
.setup(|app| {
    // ...дешева підготовка (теки тощо)...

    // Показати й сфокусувати головне вікно ЯКОМОГА РАНІШЕ — поки діє
    // foreground-activation grant від запуску. `visible:false` у конфігу
    // потрібен, щоб встигла застосуватись збережена позиція (window-state)
    // ДО появи вікна. Показ тут (а не з JS після завантаження даних)
    // гарантує, що webview ініціалізується вже у foreground — це й потрібно
    // NVDA, щоб приєднатися до документа й озвучувати фокус.
    if let Some(main_window) = app.get_webview_window("main") {
        let _ = main_window.show();
        let _ = main_window.set_focus();
    }

    // ...решта setup (важка ініціалізація може йти після цього)...
    Ok(())
})
```

**Фронтенд:** прибрати `show()`/`setFocus()` з JS. Після завантаження даних — лише перевести фокус на перший інтерактивний елемент:

```ts
// Вікно вже видиме й foreground (показане з Rust setup), тож NVDA приєднаний.
firstNavItem?.focus();
```

## Що НЕ працює (перевірені глухі кути)

- **Затримка DOM-фокусу** до OS-події foreground / через `setTimeout`/`requestAnimationFrame`. Якщо вебв'ю вже приєдналося у фоні — пізній фокус не озвучується.
- **`setFocus()` з JS після `await`** даних. Foreground grant уже згорів — Windows ігнорує запит.
- Розраховувати на `role="application"`, що він «змусить» озвучити. Навпаки: `role="application"` вимикає browse mode, тож пропущена focus-подія = повна тиша (немає фолбеку «прочитати документ»).

## Компроміси й нюанси

- **Блимання порожньою оболонкою:** показ до завантаження даних означає короткий показ ще не заповненого UI. Оболонка (навігація тощо) зазвичай рендериться миттєво; покажи стани завантаження в панелях. Для доступності це прийнятний компроміс.
- **Стрибок позиції вікна:** показуй **після** того, як плагін збереження стану вікна відновив розмір/позицію (у Tauri — `tauri-plugin-window-state` робить це під час створення вікна, тож показ у `setup()` уже коректний).
- **Окремий нюанс — browse mode замість focus mode:** навіть коли NVDA озвучує, він зрідка лишається в browse mode. Це інша проблема, пов'язана з `role="application"` і таймінгом приєднання; розглядати окремо.

## Коли застосовувати цю нотатку

- Десктоп на **Tauri / Electron / будь-якому embedded Chromium** на **Windows**.
- Вікно стартує **прихованим** і показується програмно.
- Скрінрідер (NVDA, імовірно й JAWS/Narrator) **мовчить на старті невідтворювано**.
