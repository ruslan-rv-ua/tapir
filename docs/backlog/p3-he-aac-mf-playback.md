# HE-AAC / HE-AACv2 відтворення (через Media Foundation)

- **Слаг:** `he-aac-mf-playback`
- **Тип:** дослідити
- **Стан:** draft
- **Зусилля:** M (декодер уже написаний на гілці `he-aac-mf`; лишилось діагностувати реальний баг відтворення + перемаршрутизувати + ретельно протестувати руками — може вирости до L)
- **Оновлено:** 2026-06-19
- **Залежності:** `player::engine` (`LiveSource`), Windows Media Foundation (`windows` crate); будує поверх #2-фіксу (`PROBE_TIMEOUT`, вже в `develop`)

## Опис

`symphonia` декодує **лише AAC-LC**. Низькобітрейтні AAC-станції (напр. SomaFM `groovesalad-16-aac`, 16 kbps — фактично **HE-AACv2** із SBR+PS) ніколи не дають придатний фрейм, тож **не відтворюються** (записуються нормально, бо запис не декодує).

**Спроба №1 (2026-06-18/19) — реалізована, але відкочена.** Зроблено повноцінний шлях через **Windows Media Foundation** (`MfAacDecoder` за трейтом `LiveDecoder`, маршрутизація AAC→MF). Автоматичне рев'ю пройдено, офлайн-декод реального потоку дав коректний PCM (1 359 872 f32 @ 32000 Hz/2ch).

**АЛЕ в реальному відтворенні зламалися ВСІ AAC-потоки** (включно з AAC-LC, який раніше нормально грав через symphonia) — їх програвало неправильно (схоже, не та швидкість/тон). Це зловив ручний тест (відкладений gate). Роботу **відкочено**, а #2-фікс (non-destructive `play_live` + `PROBE_TIMEOUT`) залишено.

**Поточний стан без цієї фічі:** HE-AAC-станції показують доброякісну помилку «timed out probing stream format» (без зависання) завдяки #2-фіксу — тобто graceful degradation уже є. Тому це **«nice to have»**, а не блокер.

### Найімовірніша причина поломки (не підтверджено)

ВСІ AAC (в т.ч. AAC-LC) маршрутизувалися в `MfAacDecoder`, чий вихідний spec (32 kHz / stereo для тест-потоку) подається в rodio через `LiveSource::sample_rate()`/`channels()`. Якщо цей spec або ресемплінг rodio неправильний — увесь MF-декодований AAC грає не з тією швидкістю/тоном. Офлайн-тест давав коректний PCM, але **жодного разу не проганяв реальний вихідний шлях rodio → пристрій** — саме цей геп і мав закрити відкладений ручний gate.

## Критерії готовності

- [ ] HE-AAC/HE-AACv2 (`groovesalad-16-aac`) відтворюється з **правильною швидкістю/тоном** на реальному пристрої
- [ ] **AAC-LC лишається на symphonia** (НЕ маршрутизувати LC у MF) — жодної регресії для станцій, що й так грали
- [ ] MP3 не зачеплено
- [ ] Проходить повний ручний gate (план, Task 5): play HE-AAC; перемикання LC/MP3 ↔ HE-AAC; record+play того ж потоку; NVDA-озвучення
- [ ] Windows «N»-видання без Media Feature Pack → доброякісна помилка (не зависання)
- [ ] `cargo test` + `cargo clippy` зелені; `pnpm test` + `pnpm vite:build` зелені

## Відкриті питання

- Реальна першопричина: неправильний repорт spec у `LiveSource` ↔ ресемплінг rodio, чи щось інше у виводі MF→rodio? (діагностувати на реальному пристрої з логами spec).
- Чи варто взагалі тримати MF-шлях, чи прийняти graceful-degradation (HE-AAC просто показує помилку)? MF виявився примхливим (cross-apartment COM, byte-stream over rtrb) — оцінити співвідношення цінність/складність.
- Перемаршрутизація: слати в MF **тільки HE-AAC**, а AAC-LC лишити symphonia — але як надійно відрізнити LC від HE-AAC на live-потоці до декоду (sniff/rewind проблема описана в плані)? Можливо: спробувати symphonia, і лише на специфічному провалі перемикатись (важко на нерозмотуваному rtrb).
- Чи патчити лише вихідний шлях на `he-aac-mf`, чи переробити маршрутизацію з нуля?
- Реальна цінність: скільки станцій у користувача — саме HE-AAC без LC/MP3-альтернативи?
