# Командна палітра — Phase 4: context-aware ранжування

> **Контекст:** blocked до реалізації [command-palette-phase-3](p2-command-palette-phase-3.md). Дизайн (ADR DA2) уже деталізований.

## Опис

ADR DA2 (§3 рішення) визначає: палітра стає **context-aware** — підіймає елементи
поточного екрана першими у результатах fuzzy-пошуку.

**Аспект 1 — Score boost за активним розділом:**

Кожен елемент результату несе тип — phase-3 вводить `action` | `song` | `navigate`
(поле `PaletteItem.type`); тип `station` з'явиться лише якщо
[command-palette-taxonomy](p2-command-palette-taxonomy.md) ухвалить пункти-потоки.
Поточний розділ (`$activeSection` у Nanostores) вже відомий глобально. Логіка
ранжування при побудові відфільтрованого списку:

| Активний екран | Буст |
|----------------|------|
| `songs` | `song`-елементи підіймаються першими |
| `browser` | `station`-елементи першими — лише якщо тип зʼявиться (taxonomy); інакше без бусту |
| `streams` | без бусту (дії вже переважають) |
| `wishlist` / `schedule` | без бусту або легкий буст `station` (уточнити) |

Реалізація: пошук у палітрі — токенізований substring **без score** (рішення
phase-3; fuzzy зі score — окремий запис
[command-palette-fuzzy-search](p2-command-palette-fuzzy-search.md)). Тому буст —
це стабільне сортування відфільтрованого списку: спершу елементи типу активного
розділу (у своєму поточному порядку), далі решта. Якщо на момент реалізації fuzzy
вже впроваджено — замість цього додавати числовий `contextBoost` до score. Зміна
не зачіпає алгоритм пошуку, лише порядок сортування.

**Аспект 2 — Mode-prefixes для фільтрування типів:**

VS Code використовує `>` у Ctrl+P для фільтрації лише команд. Аналог для Tapir:

| Префікс | Показує |
|---------|---------|
| `>` | лише команди (`action`) |
| `@` | лише контент: станції + пісні (`station`, `song`) |
| *(без префікса)* | все |

Парсинг у існуючій логіці input-обробника: якщо перший символ запиту `>` або `@` —
відтяти префікс перед передачею в fuzzy-search і застосувати фільтр за типом до
результатів. Зміна локальна — не торкається ні Rust-бекенду, ні Tauri IPC.

## Критерії готовності

**Context-aware ранжування:**
- [ ] `$activeSection` читається у логіці побудови результатів палітри
- [ ] Буст застосовується при сортуванні (групування типів для substring; `contextBoost` до score, якщо є fuzzy) — song-елементи першими на Songs; station-елементи на Browser, якщо тип існує
- [ ] При відсутності збігів типу з активним розділом порядок не ламається
- [ ] Юніт-тест: задані елементи + активний розділ → очікуваний порядок результатів

**Mode-prefixes:**
- [ ] Введення `>` фільтрує список до типу `action`
- [ ] Введення `@` фільтрує список до типів `station` і `song`
- [ ] Введення без префікса показує всі типи (поведінка не змінюється)
- [ ] Prefix-символ не передається у fuzzy-запит (відтинається перед пошуком)
- [ ] Плейсхолдер input-поля підказує синтаксис (напр. `Пошук · > команди · @ контент`) — доступний для NVDA як `placeholder`/`aria-label`
- [ ] Юніт-тест: prefix-парсинг + фільтрація за типом

**Доступність:**
- [ ] Динамічний reranking не скидає фокус і не зачіпає `aria-live`-регіон зайвими оголошеннями (дебаунс або `aria-atomic="false"`)
- [ ] NVDA коректно зачитує результати після введення prefix-символа

## Відкриті питання

1. **Чи потрібні mode-prefixes взагалі?** VS Code має `>` лише для команд і це
   добре відоме. Для Tapir — менш очевидно: аудиторія вузька (один користувач),
   NVDA-користувач вводить символи наосліп. Ризик: `>` і `@` не зрозумілі без
   навчання. Альтернатива — лише context-aware busting без prefixes, зробити простіше.

2. **NVDA + динамічний reranking:** якщо результати переупорядковуються під час
   введення, NVDA може зачитати весь список заново. Перевірити: чи `aria-live="polite"`
   з дебаунсом (вже використовується у fuzzy-пошуку) достатньо, чи потрібен
   `aria-relevant="additions"` замість дефолтного.

3. **Поріг бусту:** актуальне лише якщо впроваджено fuzzy-score
   ([command-palette-fuzzy-search](p2-command-palette-fuzzy-search.md)) — перекривати
   хороший збіг іншого типу чи лише при рівних score? Для substring-варіанта питання
   не стоїть (буст = стабільне групування типів). Визначити через ручне тестування
   після реалізації Phase 3.

4. **Wishlist і Schedule:** яку пріоритизацію дати там? Wishlist містить станції →
   буст `station`? Schedule містить записи → без бусту? Визначити при реалізації.
