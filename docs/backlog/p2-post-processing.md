# Постпроцесинг: запуск зовнішніх програм після запису

- **Слаг:** `post-processing`
- **Тип:** ідея
- **Стан:** draft
- **Зусилля:** M
- **Оновлено:** 2026-06-15
- **Залежності:** Phase 1 — Core Recording (✅ реалізовано); зокрема подія завершення треку та фіналізація файлу

## Опис

Після того як трек зафіналізовано (файл закрито і готовий до обробки), Tapir запускає зовнішню програму або скрипт, щоб автоматично виконати перетворення, нормалізацію або завантаження.

Типові сценарії використання:

- **Конвертація формату** — `ffmpeg -i %file output.mp3` або `%file -o %file.flac` для стиснення без втрат.
- **Нормалізація гучності** — `ffmpeg-normalize %file -o %file`, `mp3gain %file`, `replaygain` тощо.
- **Теги та метадані** — виклик `id3tag`, `beets`, або власного скрипту для вставки артиста/назви/дати.
- **Завантаження у хмару** — `rclone copy %file remote:radio/`, `aws s3 cp %file s3://bucket/` тощо.
- **Власна автоматизація** — будь-який виконуваний файл (.exe / .bat / .sh / .ps1 з обгорткою).

Функція не є критичною для базового запису, але суттєво підвищує цінність для досвідчених користувачів, які інтегрують Tapir у свій медіа-workflow.

## Технічна реалізація

### Backend (Rust)

**Модуль `postprocess::runner`:**
- Черга (`VecDeque` або `tokio::sync::Semaphore`) для обмеження кількості одночасних процесів (налаштовується, дефолт: `N = 2`).
- Запуск через `std::process::Command` / `tokio::process::Command`; на Windows — `CommandExt::creation_flags(CREATE_NO_WINDOW)`, щоб консоль не спливала.
- Підстановка placeholders у рядку аргументів: `%file` (повний шлях), `%artist`, `%title`, `%date`, `%duration`.
- Timeout з примусовим `kill()` через `tokio::time::timeout` (дефолт: 120 с, конфігурується).
- Токен скасування (`CancellationToken` з `tokio_util::sync`) — для чистого shutdown при закритті застосунку.
- Збір `stdout`/`stderr` у кільцевий буфер (останні 1000 рядків) для відображення в UI за потреби.

**Команди IPC (`commands/postprocess_commands.rs`):**
- `get_postprocess_config` → повертає поточну конфігурацію.
- `save_postprocess_config` → зберігає; валідує шлях до виконуваного файлу (файл існує й має біт execute або `.exe`).
- `get_postprocess_log` → повертає останні N рядків stdout/stderr поточного або останнього завдання.

**Тригери запуску:**
- `OnTrackComplete` — трек завершено коректно (отримано метадані або розмір > мінімального порогу).
- `OnTrackIncomplete` — запис перервано (втрата потоку, помилка мережі); дозволяє, наприклад, видалити сміттєвий файл.
- `Always` — запускати незалежно від результату.

### Frontend (React 19)

**`PostprocessSettings.tsx`** у розділі налаштувань:
- Поле «Шлях до програми» з кнопкою «Огляд» (`open` dialog через Tauri).
- Поле «Аргументи» з підказкою про доступні placeholders (`%file`, `%artist`, `%title`, …).
- Числове поле «Timeout (сек)».
- Числове поле «Макс. паралельних процесів».
- Чекбокс/радіо «Тригер»: «Завершений трек» / «Незавершений трек» / «Завжди».
- Кнопка «Тест» — запускає програму з тестовим файлом (або порожніми змінними) і показує перші N рядків виводу.

### Зберігання конфігурації

Конфіг постпроцесингу доцільно зберігати **у профілі** (разом з іншими налаштуваннями профілю), а не глобально, — щоб різні профілі могли мати різні пайплайни обробки (наприклад, один профіль конвертує у MP3, інший завантажує у хмару). Питання залишається відкритим (див. нижче).

## Безпека (OWASP)

- **Injection (A03):** аргументи командного рядка передаються як масив рядків (`args: Vec<String>`), а не конкатенуються в shell-рядок. Жодних `sh -c "…"` / `cmd /c "…"` з підстановкою введення користувача.
- **Підтвердження перед першим запуском:** при першому збереженні конфігурації показати діалог підтвердження з текстом команди — щоб випадкове виконання довільного бінарника не відбулось непомітно.
- **Обмеження шляху:** перевірити, що виконуваний файл є абсолютним шляхом (або знаходиться в `PATH`); відкидати відносні шляхи з `..`.
- **Обмеження виводу:** не відображати вивід процесу безпосередньо в `innerHTML`; рендерити як plaintext.
- **Не зберігати секрети:** якщо користувач передає токени у аргументах — це його відповідальність; у документації попередити.

## Доступність (NVDA)

- Після постановки завдання в чергу — `aria-live="polite"` анонс: «Постпроцесинг розпочато: `<назва треку>`».
- Після завершення (успіх або помилка) — `aria-live="assertive"` анонс: «Постпроцесинг завершено» або «Помилка постпроцесингу: `<перший рядок stderr>`».
- Кнопка «Тест» після кліку оновлює `aria-label` на стан: «Виконується…» → «Тест завершено».
- Поле виводу логу — textarea тільки для читання з `aria-label="Лог постпроцесингу"`.
- Усі поля налаштувань мають явні `<label>` або `aria-label`; React Aria Components для доступних контролів.

## i18n

- Ключі у `src/i18n/messages/uk.json` і `en.json`.
- Усі повідомлення про помилки, статуси черги та анонси — через Paraglide.js.

## Відкриті питання

- **Де зберігати конфіг?** У профілі (гнучко, але кожен профіль налаштовується окремо) чи глобально (простіше, але спільне для всіх профілів)? Поточна гіпотеза — у профілі.
- **Обробка помилок:** якщо постпроцесор завершився з ненульовим кодом — лише записати в лог, чи показати сповіщення користувачу? Чи заблокувати наступний запис?
- **Показувати лог у UI?** Textarea з останніми рядками stdout/stderr — корисно для діагностики, але ускладнює UI. Можливо, лише у розгорнутій панелі або у вікні «Деталі».
- **Що робити, якщо черга переповнена?** Відкидати нові завдання чи блокувати запис до звільнення черги?
- **Взаємодія з профілями (Phase 3F):** чи успадковується конфіг постпроцесингу при дублюванні профілю?
- **Windows-специфіка:** чи потрібна підтримка `.bat`/`.ps1` через обгортку `cmd /c` або `powershell -File`? Якщо так — це виняток із правила «без shell interpolation», потребує окремого підходу.
