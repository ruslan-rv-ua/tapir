# Bandwidth Limiting (Підфаза 3I-4)

- **Слаг:** `bandwidth-limiting`
- **Тип:** ідея
- **Стан:** draft
- **Зусилля:** M
- **Оновлено:** 2026-06-15
- **Залежності:** Phase 1 ✅ — `stream::connection`

## Опис

Обмеження пропускної здатності на потік (кБ/с per-stream), щоб не насичувати мережевий
канал при одночасних записах. Throttling вбудовується у `stream::connection` як шар між
HTTP-стрімом і споживачами (рекордер, плеєр).

### Чому P3 (відкладено / під сумнівом)

Радіо-потоки мають **фіксований бітрейт** встановлений сервером — типово 128–320 kbps
(~16–40 KB/s). Це вже невеликий об'єм: навіть 10 одночасних потоків займають ~400 KB/s,
що не насичує жоден сучасний широкосмуговий канал. Потреба в throttling виникає лише у
крайніх сценаріях:

- дуже вузький канал (мобільний інтернет < 1 Мбіт/с) — і водночас >5 одночасних записів;
- мережа з QoS-обмеженнями, де будь-який постійний потік треба обмежити;
- тестування: симуляція повільного з'єднання без стороннього трафіку.

Поки реального кейсу «канал насичується» від користувача не зафіксовано — реалізація
відкладена.

**Тригер повернення:** конкретні скарги від користувачів на насичення каналу при >5
одночасних записах, або вимога тестування повільних потоків у середовищі CI.

### Технічна реалізація

**Варіант A — ручний токен-бакет (`tokio::time::sleep`)**

Усередині циклу читання байтів `stream::connection` вимірювати, скільки байт прочитано
за останній інтервал; якщо пересікаємо ліміт — `tokio::time::sleep` до наступного вікна:

```rust
// Псевдокод — показує підхід, не остаточний API
loop {
    let chunk = response.chunk().await?;
    total_bytes += chunk.len();
    if let Some(limit_bps) = throttle_kbps {
        let elapsed = start.elapsed();
        let allowed = (limit_bps as u64 * 1024) * elapsed.as_secs_u64() / 1000;
        if total_bytes as u64 > allowed {
            tokio::time::sleep(Duration::from_millis(50)).await;
        }
    }
}
```

Плюси: нульові залежності. Мінуси: груба гранулярність, можливе «підстрибування» при
великих чанках.

**Варіант B — `governor` crate (rate-limiter middleware)**

Crate `governor` реалізує GCRA (Generic Cell Rate Algorithm) — точний токен-бакет без
ручного таймера. Інтегрується у `AsyncRead`-обгортку над `reqwest::Response`:

```toml
governor = "0.8"
```

```rust
// Обгортка AsyncRead з RateLimiter
struct ThrottledStream<S> { inner: S, limiter: Arc<RateLimiter<...>> }
```

Плюси: точність, стандартне рішення, не блокує Tokio. Мінуси: ще одна залежність; GCRA
може буферизувати burst і потім «гальмувати» — важко передбачити поведінку на великих
метадата-чанках.

**Рекомендований старт:** Варіант A для proof-of-concept; якщо потрібна точність — B.

### Per-stream vs глобальний ліміт

| Рівень | Переваги | Недоліки |
|--------|----------|---------|
| Per-stream | Просто: один параметр у `RecordingTask` / `PlayerEngine` | Не обмежує сумарний трафік |
| Глобальний | Обмежує сумарний трафік | Треба розподілювати між активними потоками; state у `recording::manager` |
| Обидва | Максимальна гнучкість | UI та конфіг ускладнюються; складніша логіка |

Для P3-ідеї достатньо per-stream; глобальний — тільки якщо виникне реальна потреба.

### Взаємодія з `PlayerEngine`

`PlayerEngine` теж відкриває `stream::connection` самостійно (окремий HTTP-запит від
рекордера). Throttling потрібно застосовувати і там — інакше плеєр обходить ліміт.
Рішення: одна `ThrottleConfig` в `AppSettings`, яка передається як у
`recording::manager`, так і в `player::engine`.

### Вплив на ICY-metadata

ICY-metadata вбудована у потік за фіксованим `metaint` інтервалом. Якщо читати байти
повільно (throttle), metadata-чанки приходять із затримкою щодо реального часу.
Наслідок: `splitter` розбиває трек пізніше — прогалина між фактичною зміною треку і
файловим розрізом буде більшою.

При обмеженні < ~32 KB/s (256 kbps) на потік 320 kbps це стане помітним. Треба
враховувати при виборі мінімального ліміту або документувати як known limitation.

### Де саме вбудовується

```
src-tauri/src/stream/connection.rs   ← тут throttle-обгортка навколо Response
src-tauri/src/recording/manager.rs  ← передає ThrottleConfig у connect()
src-tauri/src/player/engine.rs      ← передає ThrottleConfig у connect()
src-tauri/src/settings/models.rs    ← нове поле BandwidthSettings
src/components/settings/            ← UI-поле (якщо вирішимо не тільки конфіг-файл)
```

## Критерії готовності

- [ ] `AppSettings` містить поле `bandwidth.per_stream_kbps: Option<u32>`
- [ ] `stream::connection::connect` приймає опційний ліміт і застосовує throttle при `Some(n)`
- [ ] Throttle активний як для рекордера, так і для плеєра
- [ ] При `throttle = None` поведінка ідентична поточній (без регресії)
- [ ] Ліміт зберігається у `data/settings.json` і підхоплюється при перезапуску
- [ ] ICY-metadata затримка задокументована як known limitation у help
- [ ] Unit-тест: `connect` з mock-відповіддю не перевищує заданий ліміт за фіксований час
- [ ] NVDA: якщо UI є — поле доступне з клавіатури, має label і підказку з одиницями

## Відкриті питання

- **Одиниці**: кБ/с чи Мбіт/с у UI? (кБ/с ближче до технічної реальності, Мбіт/с —
  звичніше для користувачів інтернету; компроміс — обидва з auto-convert)
- **UI vs тільки конфіг-файл**: чи потрібен взагалі UI-контрол, якщо фіча P3? Редагування
  `settings.json` вручну може бути достатнім для такого рідкісного кейсу
- **Глобальний ліміт**: чи додавати `bandwidth.total_kbps: Option<u32>` одразу, чи тільки
  per-stream для початку?
- **Мінімальний поріг**: яке мінімальне значення дозволяти (напр. 16 KB/s = 128 kbps)?
  Нижче — ICY-metadata буде некоректно розрізатись; треба валідація з попередженням
- **`governor` crate**: чи варта залежність ради поліпшення точності? Перевірити ліцензію
  (governor = Apache-2.0 / MIT — ок) і розмір бінаря
