# Log Rotation (Фаза 3I-3)

- **Слаг:** `log-rotation`
- **Тип:** ідея
- **Стан:** draft
- **Зусилля:** S
- **Оновлено:** 2026-06-15
- **Залежності:** немає (незалежна)

## Опис

Tapir записує діагностику у `tapir.log`. Якщо застосунок працює безперервно (autostart,
тривалі записи, планувальник), цей файл може рости нескінченно — гігабайти за місяці.
Для portable EXE без інсталятора системного log management не існує (journald/Event Viewer
не задіяні), тому єдиний захист — власна ротація.

Мета: автоматично обмежити розмір лог-файлу так, щоб `tapir.log` і архіви разом ніколи
не займали більше ~20–30 МБ, незалежно від часу роботи застосунку.

### Проблема детальніше

| Сценарій | Ризик |
|----------|-------|
| Autostart + 24/7 запис | Лог росте постійно; через рік — сотні МБ |
| Детальний рівень `debug` при діагностиці | Декілька МБ за кілька хвилин |
| Portable EXE на малому диску (USB) | Лог забиває носій |
| Незрячий користувач не перевіряє `data/` | Проблема непомітна до критичного стану |

Для незрячого розробника, який діагностує проблеми з NVDA-інтеграцією виключно через
лог-файли (без візуального інтерфейсу відлагодження), надійність і доступність логів
критично важлива — але не їх нескінченний розмір.

### Технічна реалізація

`tauri-plugin-log` підтримує дві стратегії ротації:

- **`MaxLinesRotate(n)`** — ротує після `n` рядків.
- **`MaxFileSizeRotate(bytes)`** — ротує після досягнення розміру файлу.

При ротації старий файл перейменовується (`.1`, `.2`, …), нові записи йдуть у свіжий
`tapir.log`. Кількість збережених архівів задається при конфігурації плагіна.

Альтернатива: `tracing-appender` з rolling strategy (`RollingFileAppender::daily()` або
`rolling::never()` + ручна ротація). Але це складніше, ніж один параметр `tauri-plugin-log`,
і вимагає виносу налаштування логера з плагіна в окремий шар — надмірно для цієї задачі.

**Рекомендована стратегія:** `MaxFileSizeRotate` (size-based), не at-launch — причина
описана нижче в розділі конфлікту з single-instance.

**Зберігання логів:**

Поточний шлях лог-файлу визначається `tauri-plugin-log` і залежить від `app_data_dir`.
Для portable EXE (де `portable.rs` перевизначає шляхи на `data/` поруч з EXE) треба
переконатися, що плагін теж пише у `data/logs/tapir.log`, а не в `%APPDATA%\tapir\`.
Можливо, потрібне явне перевизначення цільового шляху через `.target(Target::new(...))`
у конфігурації плагіна.

### Конфлікт із single-instance (Phase 3E ✅)

`tauri-plugin-single-instance` забезпечує, що лише одна інстанція застосунку працює
повноцінно. Проте при запуску друга інстанція (яка виявляє, що перша вже є) не миттєво
завершується — вона встигає ініціалізуватися частково, зокрема може ініціалізувати
`tauri-plugin-log`.

Якби ротація відбувалась **at-launch** (стратегія `KeepOne` — видалити або перейменувати
`tapir.log` при старті), друга інстанція:
1. Перейменовує `tapir.log` першої інстанції → `tapir.log.1`.
2. Першої інстанції відкритий файловий дескриптор вказує на уже перейменований файл.
3. Перша інстанція продовжує писати у `tapir.log.1`, а новий `tapir.log` — порожній.
4. Архів раптово зникає або затирається.

**Безпечна стратегія — size-based (`MaxFileSizeRotate`)**: ротація відбувається під час
запису черговий рядок лога, коли файл вже досяг ліміту. Обидві інстанції при цьому
відкривають той самий файл для дозапису (append). На Windows файл відкрито кількома
процесами, але за короткий час (~100 мс до detect + exit) другої інстанції ризик
одночасного `rotate` мінімальний, а якщо й відбудеться — це просто лишній архів, не
втрата даних.

**Висновок:** at-launch ротація (`KeepOne`, `TimestampedRotate`) **несумісна** з
single-instance архітектурою Tapir. Слід використовувати виключно size-based ротацію.

### Параметри (пропозиція дефолтів)

| Параметр | Пропозиція | Обґрунтування |
|----------|-----------|---------------|
| `max_file_size` | 5 МБ | Достатньо для місяців роботи на рівні `info` |
| `max_archives` | 3 | Разом з `tapir.log` — ~20 МБ максимум |
| Директорія | `data/logs/` | Portable-конвенція проєкту |
| Рівень за замовч. | `info` | `debug` тільки при діагностиці |

### Налаштовуваність

На цьому етапі (ідея) відкрите питання, чи варто виносити параметри ротації до
`SettingsDialog`. Аргументи:
- **За:** досвідчений користувач може захотіти `10 МБ × 5 архівів` або `1 МБ × 10`.
- **Проти:** це технічна деталь, яку переважна більшість ніколи не зачіпне; додає UI-
  складність заради мінімальної цінності.

Мінімальна реалізація: hardcoded дефолти. Розширена: одне поле у Advanced settings.

## Критерії готовності

- [ ] Логи ротуються при досягненні макс. розміру (не при старті)
- [ ] Стратегія ротації — `MaxFileSizeRotate`, не at-launch
- [ ] Ротація не конфліктує із single-instance (Phase 3E): друга інстанція не затирає лог першої
- [ ] Лог-файли зберігаються у `data/logs/` (portable-шлях поруч з EXE, не `%APPDATA%`)
- [ ] Кількість архівних файлів обмежена (дефолт: 3)
- [ ] Загальний обсяг логів не перевищує ~20 МБ при будь-якому часі роботи

## Прийняті рішення

| Питання | Рішення |
|---------|--------|
| Розмір і кількість файлів? | **Налаштовуване через SettingsDialog** з дефолтами 5 МБ × 3 архіви. |
| Маркер в лозі при ротації? | **Так, додати `=== log rotated ===`** для діагностики NVDA-проблем. |
| Portable шлях (`data/logs/`)? | Треба перевірити чи `tauri_plugin_log` поважає `portable::log_dir()`. Якщо ні — додати в `portable.rs`. |
| Впроваджувати ротацію зараз? | **Так**, size-based стратегія (не at-launch, щоб не конфліктувати з single-instance). |
