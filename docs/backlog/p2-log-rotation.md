## Опис

Tapir записує діагностику у `tapir.log`. Якщо застосунок працює безперервно (autostart,
тривалі записи, планувальник), цей файл може рости нескінченно — гігабайти за місяці.
Для portable EXE без інсталятора системного log management не існує (journald/Event Viewer
не задіяні), тому єдиний захист — власна ротація.

Мета: автоматично обмежити розмір лог-файлу так, щоб `tapir.log` і архів разом ніколи
не займали більше ~20 МБ, незалежно від часу роботи застосунка, **і щоб при ротації
не втрачався попередній діагностичний контекст**.

### Проблема детальніше

| Сценарій | Ризик |
|----------|-------|
| Autostart + 24/7 запис | Лог росте постійно; через рік — сотні МБ |
| Детальний рівень `debug` при діагностиці | Декілька МБ за кілька хвилин |
| Portable EXE на малому диску (USB) | Лог забиває носій |
| Незрячий користувач не перевіряє `data/` | Проблема непомітна до критичного стану |

Для незрячого розробника, який діагностує проблеми з NVDA-інтеграцією виключно через
лог-файли (без візуального інтерфейсу відлагодження), надійність і доступність логів
критично важлива — але не їх нескінченний розмір. Звідси друга вимога: ротація не
має знищувати попередній зріз логу (див. вибір стратегії нижче).

### Технічна реалізація (фактичний API плагіна)

`tauri-plugin-log` (Cargo.toml: `"2"`, у Cargo.lock зафіксовано **2.8.0**) надає три
стратегії ротації:

```rust
pub enum RotationStrategy {
    KeepAll,          // усі логи з датою в імені (необмежено росте)
    KeepOne,          // ЛИШЕ поточний файл: старий ВИДАЛЯЄТЬСЯ при ротації (~1× max_size)
    KeepSome(usize),  // поточний + до N датованих архівів (~(N+1)× max_size)
}
```

Перевірено по сорсу 2.8.0 (`RotatingFile`): ротація спрацьовує у **двох** точках —

1. **При запуску** — `RotatingFile::new` (ініціалізація плагіна) перевіряє розмір
   наявного файлу і ротує, якщо `current_size >= max_size`; для `KeepSome` тут же
   підчищаються зайві старі архіви.
2. **При записі** — `flush()` ротує, коли `current_size + buffer > max_size`.

Механіка ротації по стратегіях: `KeepAll`/`KeepSome` перейменовують поточний файл у
датований (`tapir_<timestamp>.log`), `KeepSome(N)` перед цим видаляє архіви понад ліміт;
`KeepOne` **просто видаляє** поточний файл (`fs::remove_file`) — жодного слоту `.1`
чи архіву не існує. Розмір задається через `.max_file_size(bytes)`, стратегія — через
`.rotation_strategy(...)`.

**Альтернатива:** `tracing-appender` з rolling strategy (`RollingFileAppender::daily()`
або `rolling::never()` + ручна ротація). Надмірна для цієї задачі — вимагає виносу
налаштування логера з плагіна в окремий шар. Не рекомендується, поки плагін покриває потребу.

**Обрана стратегія:** `KeepSome(1)` — поточний файл + один датований архів,
разом ≤ ~2× `max_size` (~20 МБ при дефолті). Саме ця стратегія гарантує, що при
ротації серед активної сесії попередній зріз не втрачається — критично для
діагностики NVDA-проблем через логи. `KeepOne` відхилено: він видаляє лог при
ротації, тобто діагностичний контекст зникає в найгірший момент (на `debug`-рівні
ротація може настати за хвилини).

### Взаємодія з single-instance (Phase 3E ✅) — захист реальний і вже є

Ротація **спрацьовує зокрема при запуску** (див. вище), тому загроза «друга інстанція
торкається/ротує `tapir.log`» — не гіпотетична: якби log-плагін ініціалізувався у другій
інстанції, `RotatingFile::new` міг би проротувати (а з `KeepOne` — видалити) спільний файл.

Захист забезпечено **порядком реєстрації плагінів**: `single_instance` реєструється
першим (`lib.rs:99`), друга інстанція робить `exit(0)` у його setup-хуці
(`single_instance.rs:12-16`) — **до** того, як ініціалізується `tauri-plugin-log`.
Лог-плагін у вмираючій інстанції не стартує, файл не торкається.

**Висновок:** твердження в `implementation-phases.md` §3E (рядок ~412) про важливість
реєстрації single-instance перед log-плагіном — **коректне, лишити як є**. Попередня
версія цього запису помилково оголошувала його «міфологією» на підставі хибного
факту «жодна стратегія не є at-launch».

| Параметр | Значення | Обґрунтування |
|----------|----------|---------------|

## Виявлені проблеми (результати ревʼю 2026-07-19)

Під час зіставлення коду, запису та **сорсу плагіна 2.8.0** виявлено:

1. **Футган `KeepAll`.** Чекбокс «Keep full history» (`GeneralTab.tsx:330-340`)
   інвертує поле `log_rotation`: вмикання → `KeepAll` → необмежене накопичення
   timestamped-файлів. Це **відновлює саму проблему**, проти якої бореться фіча.
   Дефолт безпечний (вимкнено → `KeepOne`), але опція — пастка для необережного користувача.

2. **Інвертована семантика поля / NVDA-дефект.** Поле `log_rotation` (true = обмежено)
   озвучується як «Keep full history» (checked = НЕ обмежено). Подвійне заперечення
   для power-user, що редагує `settings.json` вручну. Проти AGENTS.md «accessibility-first».

3. **Хибне розуміння `KeepOne`.** Попередня версія запису стверджувала, що `KeepOne`
   перейменовує старий файл у слот `.1` і зберігає «один повний попередній зріз»
   (~2× max_size). Насправді `KeepOne` **видаляє** старий файл (`fs::remove_file`,
   сорс 2.8.0) — реальний ліміт ~1× max_size, а попередній контекст втрачається
   повністю. Бажану поведінку дає `KeepSome(1)`.

4. **Хибне «at-launch не існує».** Попередня версія оголошувала single-instance-конфлікт
   «міфологією», бо «жодна стратегія не at-launch». Насправді ротація відбувається і
   при ініціалізації плагіна (запуск), і при записі. Висновок «конфлікту немає» вірний,
   але з іншої причини — порядок реєстрації плагінів; твердження у §3E коректне.

5. **Розходження версії:** запис посилався на «v2.9.0»; Cargo.lock фіксує 2.8.0.

6. **Розходження «Прийняті рішення» vs код** (історичне): «5 МБ × 3 архіви» проти
   фактичних `log_max_size_mb: 10` + `KeepOne`. Поле «кількість архівів» не існує
   ні в схемі, ні в UI.

7. **Гепи плану реконсиляції** (виправлено в цій версії): TS-тип `logRotation`
   у `src/lib/tauri.ts:95` і фікстури в 6 тест-файлах не були охоплені; у
   `docs/data-models.md` — **пʼять** входжень (рядки ~62, 86, 122, 1048, 1120), не два.

8. **Нереалізований маркер ротації** (див. «Прийняті рішення» — відкладено).

## Налаштовуваність

Залишається єдине налаштовуване поле — **макс. розмір файлу** (МБ, 1–100) у Advanced
settings. Стратегія фіксована (`KeepSome(1)`), кількість архівів не налаштовується.

Обґрунтування: досвідчений користувач, якому мало 10 МБ, збільшить до 50 — цього
достатньо. Додаткові важелі («кількість архівів», «стратегія») додають UI-складність
заради мінімальної цінності і відкривають пастку `KeepAll`. За потреби повернутись до
`KeepSome(N>1)` — як майбутнє розширення.
