# Crash Recovery — відновлення записів після аварійного завершення

- **Слаг:** `crash-recovery`
- **Тип:** ідея
- **Стан:** draft
- **Зусилля:** M
- **Оновлено:** 2026-06-15
- **Залежності:** Phase 1 (✅ реалізовано) — `graceful_shutdown`, `active_recording_urls` вже є в коді

## Опис

Під час активного запису радіо-потоку процес може завершитись аварійно: вимкнення
живлення, `End Task` у Task Manager, паніка в Rust-потоці, зависання системи.
У такому разі:

- MP3/AAC-файли залишаються **незафіналізованими** (у більшості контейнерів — без
  кінцевого маркера; деякі плеєри їх не відкриють).
- ICY-теги поточного треку **не записані** (пишуться при зміні треку або зупинці).
- Частково записаний трек є «зависшим» у файловій системі без явної позначки
  кінця.
- Профіль зберігається тільки при чистому виході — `active_recording_urls` містить
  **застарілий** список (або порожній), тому після рестарту сліпий resume за цим
  полем хибний.

**Завдання фази:** виявити, що попередній сеанс завершився аварійно, відновити
активні записи і повідомити користувача (NVDA-сумісно).

### Механіка виявлення збою

`clean_shutdown` — булевий прапор у `data/state.json` (окремий від профілю):

- записується `false` при кожному **старті** (атомарний write);
- перезаписується `true` в `graceful_shutdown` перед виходом.

Якщо при старті значення `false` (або файл відсутній) — попередній сеанс
завершився аварійно.

### Чому потрібен живий снапшот

`active_recording_urls` у `Profile` оновлюється **лише** в `graceful_shutdown`.
Після збою цей список застарілий або порожній — resume за ним відновить не ті
потоки. Тому потрібен **окремий щоденний снапшот** у `data/state.json`, що
оновлюється під час роботи кожні N секунд. Тільки при `clean_shutdown = false`
цей снапшот береться для resume; при чистому виході — звичайний шлях через профіль.

### Resume-споживач

`active_recording_urls` у `Profile` вже зберігається, але **споживача немає** —
поле є в типах, але ніде на старті не читається. Необхідно при виявленому збої
прочитати URL-и з живого снапшота і запустити записи через `stream::manager`.

### Взаємодія з NVDA

Модальний діалог «Відновити записи?» — **погана ідея** для сліпого користувача:
він блокує решту UI і потребує явного підтвердження. Дружній до NVDA дефолт —
**тихий авто-resume** + анонс через `aria-live`:

- «Відновлено N записів після аварійного завершення» — якщо resume успішний.
- «Попередня сесія завершилась аварійно, відновити записи не вдалося» — якщо
  потоки недоступні.

Анонс через `LiveAnnouncer` (`data-live-announcer`) — поза модалом, одразу після
старту, коли DOM готовий.

## Критерії готовності

- [ ] `data/state.json` містить поле `clean_shutdown: bool`
- [ ] При кожному старті `clean_shutdown` записується `false` (атомарний write)
- [ ] В `graceful_shutdown` перед виходом `clean_shutdown` записується `true`
- [ ] Під час роботи (`StreamManager`) URL активних записів записуються у
  `data/state.json` (живий снапшот) з інтервалом ≤ 30 с
- [ ] На старті: якщо `clean_shutdown = false` — бекенд читає живий снапшот і
  запускає записи (resume-споживач, якого зараз немає)
- [ ] Поведінка при виявленому збої узгоджена й реалізована (тихий авто-resume
  або явний вибір — вирішити на початку фази)
- [ ] Фронтенд отримує подію після resume і виводить `aria-live` анонс
- [ ] NVDA озвучує підсумок відновлення одразу після завантаження UI
- [ ] Часткові файли записів (з моменту збою) позначені або залишені без змін —
  поведінка з ними задокументована
- [ ] Тест: `pnpm test` та `pnpm vite:build` проходять

## Відкриті питання

1. **Авто-resume vs діалог:** тихий авто-resume + live-анонс (дружньо до NVDA,
   рекомендовано) **або** діалог з варіантами «Відновити» / «Пропустити» (вимагає
   focus-trap, aria-modal, підтвердження — вартість вища). Вирішити перед стартом
   кодування.

2. **Partial-файли після збою:** що робити з MP3/AAC-файлом, що не завершився
   коректно?
   - **Залишити як є** — плеєр може відтворити більшу частину; мінімальний ризик
     втрати.
   - **Спробувати finalize** — дописати кінцевий маркер (де можливо для формату);
     може пошкодити файл при неправильному offset.
   - **Помітити суфіксом** (`_crash.mp3`) — ясно, але змінює ім'я файлу.
   Рекомендація: залишити як є, зафіксувати в лозі.

3. **Частота снапшота:** щоб мінімізувати disk I/O, але тримати точний список —
   кожні 15–30 секунд або при зміні складу записів (старт/зупинка). Тригер на
   зміну — точніше і дешевше; таймер — safety net.

4. **Resume при зміні IP/мережі:** відновлення після збою і відновлення після
   втрати з'єднання — різні сценарії. Scope цієї фази — лише рестарт після збою;
   reconnect-логіка (`stream::manager`) — окрема задача.

5. **Планові записи:** `manual_resume_urls` вже фільтрує scheduler-owned потоки —
   після збою їх resume лежить в catch-up механізмі планувальника, а **не** в
   цій фазі. Перетин не має виникати, але варто явно перевірити.

6. **Атомарний write `state.json`:** щоб уникнути пошкодженого файлу при збої під
   час запису прапора — писати у тимчасовий файл, потім `rename`. Вже практикується
   у профілі — копіювати підхід.
