# Backlog

Папка ідей, питань на дослідження та запланованих задач.
Виконаний запис просто видаляй — історія зберігається в git.

Файли сортуються за пріоритетом автоматично: спочатку `p0-`, потім `p1-`, потім `p2-`.
Всередині рівня — за алфавітом slug; порядок між однорівневими записами теж значущий
(верхній — наступний).

---

## Беклог vs фази

`implementation-phases.md` — офіційний roadmap. Якщо тема вже є фазою там — вона живе
**там**. Беклог — для того, що **ще не стало фазою**: сирі ідеї, дослідження, побічні
followup'и поза фазами.

Типовий шлях: `ідея` → `дослідити` → `заплановано` → промотуй у фазу → видаляй запис.

---

## Як назвати файл

Формат: **`p<рівень>-<slug>.md`**

- Рівень — число пріоритету: `0`, `1`, `2`.
- Slug — короткий англомовний ідентифікатор через дефіси, стабільний (не змінюється).
- Приклад: `p0-crash-recovery.md`

Сортування імен файлу дає чергу: спочатку `p0`, потім `p1`, потім `p2`.

---

## Позначки

### Пріоритет

Кодується **лише у префіксі імені файла**.

| Рівень | Значення | Коли |
|--------|----------|------|
| `P0` (`p0-`) | терміново, робити зараз | блокує, ризик втрати даних, критичний баг |
| `P1` (`p1-`) | найближчим часом | готовий до реалізації, висока/середня цінність |
| `P2` (`p2-`) | пізніше | низька цінність, polish, коли дійдуть руки |

### Тип (природа запису)

| Значення | Зміст |
|----------|-------|
| `ідея` | сирі думки, без зобов'язань |
| `дослідити` | треба з'ясувати підхід/технологію/вимоги |
| `заплановано` | рішення прийнято, реалізуємо |

Життєвий цикл: `ідея` → `дослідити` → `заплановано` → (готово — файл видаляємо).

### Стан (готовність до роботи)

| Значення | Зміст |
|----------|-------|
| `draft` | ще формується, не брати в роботу |
| `ready` | можна братися |
| `blocked` | чекає на щось — вказати що саме у полі «Блоковано» |

### Зусилля (орієнтовна оцінка)

| Значення | Зміст |
|----------|-------|
| `S` | кілька годин — один невеликий компонент |
| `M` | кілька днів — кілька компонентів або складний алгоритм |
| `L` | тиждень+ — системна зміна, кілька шарів |

## Шаблон файлу запису

Запис завершується секцією **«Промпт для агента»** — посиланням на каталог промптів
нижче. Відкрий каталог, скопіюй потрібний промпт і підстав конкретику.

````markdown
# <Назва>

- **Слаг:** `<slug>`
- **Тип:** ідея · дослідити · заплановано
- **Стан:** draft · ready · blocked
- **Зусилля:** S · M · L
- **Оновлено:** YYYY-MM-DD
- **Залежності:** що має бути готовим

## Опис
Коротко: що і навіщо.

## Критерії готовності
- [ ] ...
- [ ] ...

## Відкриті питання
- ...

## Блоковано
- чим і чому (тільки для стану blocked)

## Документи
- [implementation-phases.md §3X](../implementation-phases.md)
- шляхи коду: `src/...`

## Промпт для агента
Каталог промптів за типом: [README — Каталог промптів](README.md#каталог-промптів-за-типом).
Скопіюй потрібний і підстав конкретику цього запису.
````

---

## Каталог промптів за типом

Кожен запис закінчується посиланням сюди. Скопіюй потрібний промпт і віддай агенту
кодування (Claude Code, GitHub Copilot тощо) — підстав конкретику запису замість `<…>`.

### Тип `дослідити`

```text
Нічого не змінюй — лише дослідження. Не редагуй файли, не створюй комітів, не запускай команд, що щось змінюють. Відповідай у чаті.

Що дослідити: <назва запису, напр. «Фаза 3 — CLI Arguments»>

Спершу вивчи поточний стан: код за темою, цей запис беклогу й пов'язані документи. Далі оціни фічу в цілому та знайди:
- незакриті питання й неоднозначності;
- гепи та ризики (технічні, UX, доступність/NVDA);
- суперечності з наявною архітектурою та конвенціями проєкту.

Критикуй, пропонуй альтернативи, уточнюй рішення. За потреби шукай в інтернеті (актуальні API, версії, практики).

Якщо є питання — став по одному: дай контекст, запропонуй варіанти відповіді й познач рекомендований. Дочекайся відповіді перед наступним питанням.

Наприкінці — коротка оцінка готовності до реалізації та список того, що треба вирішити перед стартом.
```

> Промпти для типів `ідея` та `заплановано` — будуть додані пізніше.

---

## Як працювати з беклогом

- **Додати запис:** створи файл `p<рівень>-<slug>.md` за шаблоном. Порядок підхопиться автоматично.
- **Підвищити пріоритет:** перейменуй файл (зміни рівень), онови тип/стан якщо потрібно.
- **Виконано:** видали файл. Історія живе в `git log`.
