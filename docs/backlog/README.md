# Backlog

Папка ідей, питань на дослідження та запланованих задач.
Виконаний запис **переміщай у [`done/`](done/)** — він лишається довідкою про ухвалені
рішення й критерії, за якими фічу приймали.

Файли сортуються за пріоритетом автоматично: спочатку `p0-`, потім `p1-`, `p2-`, `p3-`.
Підпапка `done/` у чергу не входить.
Всередині рівня — за алфавітом slug; порядок між однорівневими записами теж значущий
(верхній — наступний).

---

## Беклог vs фази

`implementation-phases.md` — офіційний roadmap. Якщо тема вже є фазою там — вона живе
**там**. Беклог — для того, що **ще не стало фазою**: сирі ідеї, дослідження, побічні
followup'и поза фазами.

Типовий шлях: `ідея` → `дослідити` → `заплановано` → промотуй у фазу → переміщай запис у `done/`.

---

## Як назвати файл

Формат: **`p<рівень>-<slug>.md`**

- Рівень — число пріоритету: `0`, `1`, `2`, `3`.
- Slug — короткий англомовний ідентифікатор через дефіси, стабільний (не змінюється).
- Приклад: `p0-crash-recovery.md`

Сортування імен файлу дає чергу: спочатку `p0`, потім `p1`, `p2`, `p3`.

## Позначки

### Пріоритет

Кодується **лише у префіксі імені файла**.

| Рівень | Значення | Коли |
|--------|----------|------|
| `P0` (`p0-`) | терміново, робити зараз | блокує, ризик втрати даних, критичний баг |
| `P1` (`p1-`) | найближчим часом | готовий до реалізації, висока/середня цінність |
| `P2` (`p2-`) | пізніше | низька цінність, polish, коли дійдуть руки |
| `P3` (`p3-`) | відкладено / під сумнівом | малоймовірно; повертатись лише за явним тригером |

### Тип (природа запису)

| Значення | Зміст |
|----------|-------|
| `ідея` | сирі думки, без зобов'язань |
| `дослідити` | треба з'ясувати підхід/технологію/вимоги |
| `заплановано` | рішення прийнято, реалізуємо |

Життєвий цикл: `ідея` → `дослідити` → `заплановано` → (готово — файл переїжджає в `done/`).

### Стан (готовність до роботи)

| Значення | Зміст |
|----------|-------|
| `draft` | ще формується, не брати в роботу |
| `ready` | можна братися |
| `blocked` | чекає на щось — вказати що саме у полі «Блоковано» |
| `done` | реалізовано й перевірено — файл живе в `done/` |

### Зусилля (орієнтовна оцінка)

| Значення | Зміст |
|----------|-------|
| `S` | кілька годин — один невеликий компонент |
| `M` | кілька днів — кілька компонентів або складний алгоритм |
| `L` | тиждень+ — системна зміна, кілька шарів |

## Шаблон файлу запису

Запис завершується секцією **«Промпт для агента»** — посиланням на каталог промптів
нижче. Відкрий каталог, скопіюй потрібний промпт і підстав конкретику.

````markdown
# <Назва>

- **Слаг:** `<slug>`
- **Тип:** ідея · дослідити · заплановано
- **Стан:** draft · ready · blocked
- **Зусилля:** S · M · L
- **Оновлено:** YYYY-MM-DD
- **Залежності:** що має бути готовим

## Опис
Коротко: що і навіщо.

## Критерії готовності
- [ ] ...
- [ ] ...

## Відкриті питання
- ...

## Блоковано
- чим і чому (тільки для стану blocked)

## Документи
- [implementation-phases.md §3X](../implementation-phases.md)
- шляхи коду: `src/...`

## Промпт для агента
Каталог промптів за типом: [README — Каталог промптів](README.md#каталог-промптів-за-типом).
Скопіюй потрібний і підстав конкретику цього запису.
````

---

## Каталог промптів за типом

Кожен запис закінчується посиланням сюди. Скопіюй потрібний промпт і віддай агенту
кодування (Claude Code, GitHub Copilot тощо) — підстав конкретику запису замість `<…>`.

### Тип `ідея`

```text
Нічого не змінюй — лише обговорення. Не редагуй файли, не створюй комітів, не запускай команд, що щось змінюють. Відповідай у чаті.

Що обговорюємо: <назва запису, напр. «Швидкий перемикач профілів»>

Це сира ідея без зобов'язань. Мета розмови — розкрити її й зрозуміти, чи варта вона роботи, а не одразу планувати реалізацію.

Спершу швидко звірся з контекстом: цей запис беклогу, пов'язаний код і документи — щоб говорити предметно, а не абстрактно.

Далі допоможи розвинути ідею:
- сформулюй проблему/потребу, яку вона розв'язує, і для кого;
- запропонуй 2–3 способи втілення з плюсами й мінусами кожного;
- зваж цінність проти складності, познач ризики й де воно зачіпає доступність/NVDA;
- чесно скажи, чи це взагалі варто робити, і яка була б простіша альтернатива.

Уточнювальні питання став по одному: дай контекст, запропонуй варіанти відповіді й познач рекомендований. Дочекайся відповіді перед наступним питанням.

Наприкінці — підсумок у 3–5 рядках і рекомендований наступний крок: відкинути, лишити як ідею, перевести в «дослідити» чи одразу в «заплановано».
```

### Тип `дослідити`

```text
Нічого не змінюй — лише дослідження. Не редагуй файли, не створюй комітів, не запускай команд, що щось змінюють. Відповідай у чаті.

Що дослідити: <назва запису, напр. «Фаза 3 — CLI Arguments»>

Спершу вивчи поточний стан: код за темою, цей запис беклогу й пов'язані документи. Далі оціни фічу в цілому та знайди:
- незакриті питання й неоднозначності;
- гепи та ризики (технічні, UX, доступність/NVDA);
- суперечності з наявною архітектурою та конвенціями проєкту.

Критикуй, пропонуй альтернативи, уточнюй рішення. За потреби шукай в інтернеті (актуальні API, версії, практики).

Якщо є питання — став по одному: дай контекст, запропонуй варіанти відповіді й познач рекомендований. Дочекайся відповіді перед наступним питанням.

Наприкінці — коротка оцінка готовності до реалізації та список того, що треба вирішити перед стартом.
```

### Тип `заплановано`

```text
Реалізуй цей запис. Рішення вже прийняте — мета довести до робочого, протестованого коду.

Що реалізуємо: <назва запису, напр. «Гарячі клавіші гучності»>

Почни зі скіла `superpowers:brainstorming` — пройди його, щоб узгодити вимоги й дизайн перед кодом, а далі веди роботу за процесом superpowers: план → реалізація через TDD → перевірка.

Перед стартом звірся з контекстом: цей запис беклогу, його критерії готовності та залежності, пов'язаний код і документи (AGENTS.md, implementation-phases.md та ін.).

Дотримуйся конвенцій проєкту з AGENTS.md. Де доречно — закладай доступність/NVDA від початку, не як доробку.

Питання, якщо виникають, став по одному: контекст, варіанти відповіді, рекомендований. Дочекайся відповіді перед наступним.

Гейти перед завершенням: `pnpm test` і `pnpm vite:build` мають проходити. Онови критерії готовності в записі; коли все зроблено — познач `**Стан:** done` з датою, перемісти файл у `docs/backlog/done/` і прибери його рядок з `IMPLEMENTATION-ORDER.md`.
```

## Як працювати з беклогом

- **Додати запис:** створи файл `p<рівень>-<slug>.md` за шаблоном. Порядок підхопиться автоматично.
- **Підвищити пріоритет:** перейменуй файл (зміни рівень), онови тип/стан якщо потрібно.
- **Виконано:** три кроки, всі обов'язкові:
  1. у записі познач `**Стан:** done` і `**Оновлено:**` датою приймання;
  2. `git mv docs/backlog/p<рівень>-<slug>.md docs/backlog/done/` — ім'я з префіксом не змінюється;
  3. прибери рядок запису зі зведеної таблиці [IMPLEMENTATION-ORDER.md](IMPLEMENTATION-ORDER.md),
     перенумеруй решту й полагодь перехресні посилання `#N` на нього.

### Навіщо `done/`, а не видалення

Записи містять ухвалені рішення й критерії приймання, на які **посилаються інші записи**
(«надбудова над #1», «координація з #15»). Після видалення такі посилання ведуть у нікуди,
а рішення доводиться відновлювати з `git log`. У `done/` вони лишаються читаними за
посиланням, не засмічуючи чергу.
