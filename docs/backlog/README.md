# Backlog

Папка ідей, питань на дослідження та запланованих задач. Кожен запис — markdown-файл
з **YAML front-matter** як єдиним джерелом правди про його стан, тип, залежності й
версію. [ROADMAP.md](ROADMAP.md) — навігація за front-matter, згрупована по `target`
(semver-версії).

Виконаний запис **переміщай у [`done/`](done/)** — він лишається довідкою про ухвалені
рішення й критерії, за якими фічу приймали (див. «Навіщо `done/`, а не видалення»).

Файли сортуються за пріоритетом автоматично: спочатку `p0-`, потім `p1-`, `p2-`, `p3-`.
Підпапка `done/` у чергу не входить. Префікс у імені файлу — лише ls-підказка сортування;
**`priority:` у front-matter — єдине джерело правди** пріоритету.

---

## Беклог vs фази

`implementation-phases.md` — офіційний фазовий roadmap застосунку. Якщо тема вже є
фазою там — вона живе **там**. Беклог — для того, що **ще не стало фазою**: сирі ідеї,
дослідження, побічні followup'и поза фазами.

Типовий життєвий цикл: `type: idea` → `type: research` → `type: planned` (`status: ready`)
→ реалізація → `status: done`, файл переїжджає в `done/`. Якщо запис виростає у велику
фічу — може промотуватись у фазу `implementation-phases.md`; тоді запис відповідно
закривається (посилання на фазу в `notes:`).

---

## Як назвати файл

Формат: **`p<рівень>-<slug>.md`**

- Рівень — число пріоритету: `0`, `1`, `2`, `3` (та сама шкала, що `priority:` у front-matter).
- `slug` — короткий англомовний ідентифікатор через дефіси, стабільний (не змінюється),
  **завжди дорівнює імені файлу без префікса `p<рівень>-`**. Без винятків і без префіксів
  на кшталт `bug-` у slug'у — природа запису кодується полем `kind:`, не іменем файлу.
- Приклад: `p0-stream-name-disambiguation.md` → slug `stream-name-disambiguation`.

Сортування імен файлу дає чергу: спочатку `p0`, потім `p1`, `p2`, `p3`.

## Схема front-matter

Кожен запис (активний і `done/`) починається з YAML front-matter. Обов'язкові поля:

| Поле | Тип | Допустимі значення | Зміст |
|------|-----|---------------------|-------|
| `slug` | string | — | = ім'я файлу без `p<рівень>-`-префікса |
| `title` | string | — | назва запису |
| `priority` | enum | `P0` \| `P1` \| `P2` \| `P3` | дублює префікс файлу; тут — джерело правди |
| `type` | enum | `idea` \| `research` \| `planned` | природа роботи: сира ідея / потребує дослідження / рішення прийнято |
| `status` | enum | `draft` \| `ready` \| `blocked` \| `done` | готовність до роботи |
| `effort` | enum | `S` \| `M` \| `L` | орієнтовна оцінка |
| `kind` | enum | `feature` \| `bug` \| `chore` | природа кінцевого результату (без `research` — те виражає `type`) |
| `target` | string | `<semver>` \| `unscheduled` | версія, у яку планується запис |
| `updated` | date | `YYYY-MM-DD` | дата останньої змістовної правки запису |
| `a11y` | bool | `true` \| `false` | чи зачіпає доступність/NVDA |
| `depends_on` | array | slug'и записів беклогу | лише записи цієї папки (вкл. `done/`) |
| `blocks` | array | slug'и записів беклогу | які записи розблоковує цей |
| `touches` | array | шляхи коду | орієнтовний scope для агента |
| `gates` | array | команди | три ворота фронтенду: `[pnpm test, pnpm typecheck, pnpm vite:build]` (усі разом — `just check`) |

Необов'язкові поля:

| Поле | Коли |
|------|------|
| `depends_on_external` | залежності поза беклогом — фази (`implementation-phases.md`), код, зовнішні системи. **Виконані (✅) залежності не вносити** — вони вже в коді, згадати можна в тілі запису. |
| `blocked_reason` | рядок, **обов'язково** при `status: blocked` |
| `notes` | масив коротких рядків — нюанси, що не ввійшли в основний опис |
| `completed` | дата `YYYY-MM-DD`, лише для `status: done` у `done/` |

Шаблон нового запису — [`_TEMPLATE.md`](_TEMPLATE.md).

### Пріоритет

| Рівень | Коли |
|--------|------|
| `P0` | терміново, робити зараз — блокує, ризик втрати даних, критичний баг |
| `P1` | найближчим часом — готовий до реалізації, висока/середня цінність |
| `P2` | пізніше — низька цінність, polish, коли дійдуть руки |
| `P3` | відкладено / під сумнівом — малоймовірно; повертатись лише за явним тригером |

### Тип (`type`) і природа результату (`kind`)

`type` — стадія роботи над записом: `idea` (сирі думки, без зобов'язань) →
`research` (треба з'ясувати підхід/технологію/вимоги) → `planned` (рішення прийнято,
реалізуємо). `kind` — незалежна вісь: що вийде в результаті (`feature`/`bug`/`chore`).
Дослідницький запис про нову фічу — `type: research, kind: feature`; дослідження вади —
`type: research, kind: bug`.

### Стан (`status`)

| Значення | Зміст |
|----------|-------|
| `draft` | ще формується, не брати в роботу |
| `ready` | можна братися |
| `blocked` | чекає на щось — `blocked_reason:` пояснює що саме |
| `done` | реалізовано й перевірено — файл живе в `done/` |

### Зусилля (`effort`)

| Значення | Зміст |
|----------|-------|
| `S` | кілька годин — один невеликий компонент |
| `M` | кілька днів — кілька компонентів або складний алгоритм |
| `L` | тиждень+ — системна зміна, кілька шарів |

### Версія (`target`)

Ручні semver-мітки (`0.2.0`, `0.3.0`, …) або `unscheduled`. Призначає розробник —
агент не переставляє `target` самостійно без явного рішення. [ROADMAP.md](ROADMAP.md)
групує записи саме за цим полем.

## Структура файлу запису

```markdown
---
<front-matter>
---

# <Назва>

> **Контекст:** 1–2 рядки — що це, статус роботи, що читати першим.

## Опис
…

## Критерії готовності
- [ ] …

## (За потребою: Відкриті питання / Прийняті рішення / Технічні деталі)

## Документи
- посилання…
```

Done-записи — та сама структура; front-matter додатково має `status: done` і
`completed: YYYY-MM-DD`.

## Алгоритм для агента

1. Відкрий [ROADMAP.md](ROADMAP.md). Поточна target-версія — найменша semver-секція
   з невиконаними записами. Знайди в ній верхній запис із `status: ready`.
   (Немає `ready` — узяти найменший `effort` з `ready` у `unscheduled`, або grooming-задачу.)
2. Відкрий файл запису. Прочитай front-matter + секцію «Контекст» + «Критерії готовності».
3. Режим роботи визначає (`type`, `status`):
   - `idea` / будь-який `type` + `draft` → **ОБГОВОРЕННЯ**: ніяких правок коду, лише аналіз і питання в чаті.
   - `research` → **ДОСЛІДЖЕННЯ**: ніяких правок коду, звіт + рекомендація.
   - `planned` + `draft` → **GROOMING**: довести до `ready` — уточнити відкриті питання, оновити front-matter.
   - `planned` + `ready` → **РЕАЛІЗАЦІЯ**: код за «Критеріями готовності», TDD, малі кроки.
   - `blocked` → **НЕ БРАТИ** (вказано `blocked_reason`), хіба що розблоковано явним рішенням.
4. Питання — по одному, з варіантами відповіді й рекомендованим; чекай відповіді.
5. Гейти перед закриттям — із front-matter `gates:`. Коли готово: `status→done`,
   `completed:<дата>`, `updated:<дата>`, `git mv` файлу в `done/` (ім'я з префіксом
   не змінюється), перенести рядок запису в секцію «Виконано» ROADMAP.

## Як працювати з беклогом

- **Додати запис:** створи файл `p<рівень>-<slug>.md` за [`_TEMPLATE.md`](_TEMPLATE.md).
  Порядок підхопиться автоматично.
- **Підвищити пріоритет:** перейменуй файл (зміни рівень) **і** онови `priority:`
  у front-matter разом — вони мають збігатись.
- **Виконано:** три кроки, всі обов'язкові:
  1. у front-matter: `status: done`, `completed:` дата приймання, `updated:` та сама дата;
  2. `git mv docs/backlog/p<рівень>-<slug>.md docs/backlog/done/` — ім'я з префіксом не змінюється;
  3. перенеси рядок запису в секцію «Виконано» [ROADMAP.md](ROADMAP.md);
  4. **перебазуй посилання.** Запис опустився на рівень глибше: у ньому `../../src/…`
     стає `../../../src/…`, а `done/p1-x.md` — просто `p1-x.md`; ті, хто посилався на
     нього ззовні, навпаки дописують `done/`. Крок легко пропустити — посилання ламаються
     тихо, запис і далі читається. Сторож — тест `build/docsLinks.test.ts` у `pnpm test`.
- **Дрейф ROADMAP vs front-matter:** front-matter — першоджерело. ROADMAP оновлюється
  при зміні будь-якого з полів `slug`/`priority`/`type`/`status`/`effort`/`target`/`depends_on`.

### Навіщо `done/`, а не видалення

Записи містять ухвалені рішення й критерії приймання, на які **посилаються інші записи**
через `depends_on:` («надбудова над playback-toggle-stop-pause», «координація з
resume-last-playback»). Після видалення такі посилання ведуть у нікуди, а рішення
доводиться відновлювати з `git log`. У `done/` вони лишаються читаними за посиланням,
не засмічуючи чергу.
