# CI на GitHub Actions: ворота, які відмовляють

> **Контекст:** правило й відкинуті альтернативи —
> [ADR «ворота відмовляють, а не радять»](../../decisions/2026-09-05-gates-refuse-rather-than-advise.md).
> Передумова — [repo-public-rename](p2-repo-public-rename.md): без публічного
> репозиторію захист гілки недоступний.

## Опис

Ворота проєкту — `pnpm vite:build`, `pnpm test`, `pnpm typecheck`, `pnpm lint`
(разом `just check`) і `cargo clippy --all-targets`, `cargo test` (разом
`just check-rust`). Усі шість запускаються локально й лише тоді, коли про них згадали.

Чернетка цього запису обґрунтовувала CI двома аргументами, і **обидва спростовані
вимірами 2026-09-05**:

- «холодний vitest інколи падає спонтанно, CI дає другий незалежний прогін» — на
  найхолоднішому можливому дереві (без `node_modules`, без кешу vite, без `dist/`)
  1176 із 1176 зелені. Правдоподібна причина флаку — паралельні сесії, що ділять одне
  робоче дерево й перемикають гілку одна під одною; у CI цього немає за побудовою;
- «тег хочеться робити на зеленому» — агент і так ганяє ворота перед закриттям
  кожного запису.

Лишається один, і він не про перевірку, а про **відмову**. Сьогодні `develop` не має
механізму, який не пустив би червоний коміт, і локальний FF-мерж такого механізму мати
не може в принципі. Ворота, які радять, у цьому проєкті вже є — це агент; ворота, які
відмовляють, з'являються лише разом із PR і захистом гілки.

Другий, слабший мотив — властивість, якої досі ніхто не перевіряв: **збірка з чистого
клону**. Локальний прогін завжди має теплий `node_modules`, згенерований і gitignored
`src/i18n/paraglide/`, теплий `target/` і, можливо, файл, який забули закомітити. На
2026-09-05 ця конфігурація зелена з обох боків — тобто CI не лікує наявну поломку, а
утримує властивість.

## Форма

**Два jobs, обидва `windows-latest`, id = name:**

- `frontend` — `pnpm install --frozen-lockfile`, далі `just check` по порядку
  (`vite:build` першим: paraglide генерується на диск, і `tsc` з тестами читають саме
  його);
- `backend` — `cargo clippy --all-targets`, `cargo test`. **Node тут не потрібен**:
  `generate_context!` у dev-профілі бере гілку з порожніми ассетами, `dist/` не читає.

Ділення саме таке не заради хвилин, а заради читабельності провалу: два рядки з
іменами замість одного довгого лога, у якому треба шукати місце обриву. Обидва jobs
незалежні й біжать паралельно.

Фронтенд свідомо **не** на `ubuntu-latest`: продукт існує лише під Windows, і ворота,
що судять з іншої платформи, дають нечесний вердикт.

**Тригери:** `pull_request` у `develop`, `push` у `develop`, `workflow_dispatch`.
Без `paths`-фільтрів — фільтр не дає перевірці відзвітувати, і PR блокується назавжди
без жодного червоного. Ціна відома й прийнята: документаційний PR платить повний прогін.

**Кеш** (`Swatinem/rust-cache` і кеш store pnpm) **пише лише прогін на `push: develop`**,
PR'и його тільки читають (`save-if`). Кеш, створений у прогоні PR, прив'язаний до цього
PR і недоступний нікому іншому, але місце в 10-гігабайтному ліміті займає й витісняє
єдиний корисний. Властивість «чистий клон» кеш не з'їдає: `actions/checkout` щоразу дає
свіже дерево, `dist/` не кешується взагалі, а `--frozen-lockfile` перевстановлює за
локом.

**`concurrency`** групується за `workflow + ref`; `cancel-in-progress` — **лише** для
`pull_request`. Прогони на `push: develop` не скасовуються ніколи: саме вони пишуть кеш.

## Налаштування GitHub

- `develop`: PR обов'язковий, перевірки `frontend` і `backend` обов'язкові,
  «Require branches to be up to date before merging» увімкнено, **адміністратор
  включений**. Ворота, які власник обходить, — це дорадчий CI під іншим ім'ям.
- Метод злиття — **тільки merge commit**; squash і rebase вимкнути в налаштуваннях.
  Merge commit — єдиний, що лишає коміти дослівно, з тими самими SHA, які перевірив CI.
  Squash зруйнував би навмисну структуру «код окремо, `docs(backlog): close …` окремо»;
  rebase переписав би SHA, які записи фіксують у `notes:`.

## Що змінюється в роботі

- **Локальний FF-мерж у `develop` зникає.** Прямий push у захищену гілку відхиляється
  (`GH006: Required status check is expected`).
- **Прийом `git fetch . <гілка>:develop` мертвий.** `develop` рухає лише GitHub, локальна
  копія стає дзеркалом і оновлюється `git pull`. Це стосується всіх паралельних worktree.
- **Процедура закриття запису дістає крок посередині:** ворота → коміт → `push` гілки →
  `gh pr create` → **дочекатись зеленого** → `gh pr merge --merge` → `git pull` →
  `done/` → рядок у ROADMAP. Веде PR агент, до кінця: запис не закривається, поки
  перевірки справді не зелені.

## Порядок увімкнення

Порядок несучий — переставляння кроків дає або заблокований PR, або осиротілі коміти.

1. ✅ Закрити [repo-public-rename](p2-repo-public-rename.md) — зроблено 2026-09-05.
2. **Запушити локальний `develop` повністю.** У мить увімкнення захисту будь-який коміт,
   що вже в локальному стовбурі, але не на origin, стає непроштовхуваним: прямий push
   відхиляється, а PR із нього не зробити — він уже не на гілці. Такі коміти доводиться
   витягувати штучною гілкою.
3. Попередити паралельні сесії про пункт «прийом мертвий» вище.
4. PR із workflow — захисту ще немає, зливається звичайно.
5. Зелений прогін показує GitHub імена `frontend` і `backend`; **тепер** вмикати захист.
6. Документація (`AGENTS.md`, `DEVELOPERS.md`) — **наступним PR, уже крізь справжні
   ворота**: документаційний PR стає першим живим прогоном процесу, який він описує.

## Свідомо відхилено

Повне обґрунтування — в ADR; тут перелік, щоб не пропонувати вдруге.

- **Дорадчий CI** (червоний хрестик постфактум) — не розв'язує задачу.
- **Обхід для адміністратора** — перетворює ворота на дорадчі.
- **Auto-merge** — агент оголошував би запис закритим, поки PR ще біжить.
- **`paths-ignore` для документації із заглушкою-двійником** — зелена перевірка, яку
  ніщо не перевіряло, і тиха поломка.
- **Ретрай будь-якого рівня**, зокрема `vitest --retry` — стирає єдиний сигнал, заради
  якого ворота ставлять.
- **Збірка exe у воротах** — окремий повний прохід release-профілю; винесено в
  [release-workflow](../p3-release-workflow.md).
