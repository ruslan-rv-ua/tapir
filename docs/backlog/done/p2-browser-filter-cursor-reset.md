# Браузер станцій — скидання курсора списку на перший елемент після зміни фільтра

> **Контекст:** обговорено й погоджено 2026-07-23. Коли користувач змінює текст
> пошуку/фільтра і список результатів оновлюється, вхід у список (Tab/F6) має
> ставити фокус на **перший** елемент — найкращий збіг нового запиту.

## Опис

`useCompositeList` пам'ятає позицію курсора (`userNavigatedRef` +
`memoryRef`), і це правильно для незмінного списку («вийшов у тулбар —
повернувся на той самий рядок»). Але після зміни фільтра стара позиція
стосується результатів *іншого* запиту:

- якщо запам'ятований елемент випадково вижив у новій вибірці — вхід у список
  падає на нього десь у середині: NVDA каже «Станція X, 7 з 12», і незрозуміло,
  чи фільтр взагалі спрацював;
- якщо не вижив — спрацьовує clamp по старому індексу, який для нової вибірки
  теж нічого не означає.

Правильна поведінка — патерн command palette / VS Code Quick Pick: після кожної
зміни запиту курсор на першому результаті. Це збігається з APG: для listbox
вхід через Tab → вибраний елемент, інакше **перший**; «повернутися туди, де був»
рекомендовано лише для grid-подібних віджетів і незмінного вмісту.

Поточний код уже робить це правильно **до першої навігації**: re-seed-ефект
([useCompositeList.ts:331-338](../../../src/hooks/useCompositeList.ts#L331-L338))
тримає активний рядок на `items[0]`, поки `userNavigatedRef` — false. Проблемний
сценарій один: користувач походив по списку стрілками (`userNavigatedRef =
true`), повернувся в поле пошуку, змінив текст — пам'ять лишається на старому
елементі.

**Рішення:** зміна фільтра/запиту, поки фокус не в списку, скидає
`userNavigatedRef` — далі наявний re-seed сам припинає курсор до першого рядка.
Найпростіша форма — імперативний метод на кшталт `resetCursor()` у handle
`CompositeList`, який BrowserPanel/StationList викликає при новій вибірці
результатів (новий запит, а не «Завантажити ще»).

## Критерії готовності

- [x] Після зміни пошукового запиту (нова вибірка результатів) вхід у список
      Tab-ом або F6 ставить фокус на перший елемент — навіть якщо користувач
      перед тим навігував по списку.
- [x] «Завантажити ще» (допис у ту саму вибірку) курсор **не** скидає.
- [x] Пам'ять позиції для незмінного списку збережена: вихід у тулбар/інша зона
      і повернення без зміни фільтра → фокус на той самий рядок (поточна
      поведінка, регресії немає).
- [x] Фокус не переноситься в список автоматично під час набору — лишається в
      полі пошуку.
- [x] `docs/help/` оновлено — або зазначено, що запис видимої поведінки не змінює.
- [x] NVDA: після зміни запиту вхід у список озвучує перший результат. Номер
      позиції («1 з N») у формулюванні критерію був припущенням — рядки списків
      Tapir не несуть `aria-posinset`/`aria-setsize` і позиції не називають;
      «перший» перевірено порівнянням з тим, що озвучує `Home`. Прогін 7/7.

## Відкриті питання

- Чи поширити те саме правило на інші списки з фільтром (якщо/коли з'являться) —
  механізм у `useCompositeList` спільний, тригер скидання лишається за
  екраном-власником.
