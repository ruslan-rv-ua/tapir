# Phase 3D — Scheduler (заплановані записи): дизайн v1

Дата: 2026-06-12
Статус: затверджено (brainstorming-сесія), очікує implementation plan

## 1. Мета й обсяг

Автоматичний запис радіопотоків за розкладом: одноразовий (дата + час) та повторюваний
(дні тижня + час). Розклади зберігаються в профілі (`Profile.scheduledRecordings` — поле
вже існує) і спрацьовують **лише для активного профілю**.

**Гарантія v1:** запис спрацьовує, лише якщо Tapir запущений (вікно або трей).
Пропуски чесно фіксуються й озвучуються.

**Свідомо поза v1** (backlog, після Фаз 3E Single Instance + 3G CLI Arguments):

- Пробудження ПК зі сну (`SetWaitableTimer` з resume-флагом).
- Запуск записів через Windows Task Scheduler із закритим Tapir (як у TapinRadio).
- Per-schedule override для padding (`Option<PaddingOverride>`, None = глобальне) —
  аддитивна зміна з `#[serde(default)]`, додається без міграцій.
- Іменування файлів за назвою розкладу (змінна `%schedule%` у шаблонах).
- Пункт «наступний плановий запис» у tray-меню; команди планувальника в command palette.
- Автозапуск із Windows (Фаза 3I) — суттєво посилює гарантію A, окремої роботи
  в 3D не потребує.

**Відоме обмеження до Фази 3E (Single Instance):** дві запущені копії Tapir
означають два незалежні планувальники → подвійне спрацювання розкладів.

## 2. Модель даних

Зміни в існуючому scaffold ([src-tauri/src/profile.rs](../../../src-tauri/src/profile.rs)).
Breaking change прийнятний — scaffold ще ніким не використовується, міграцій у проєкті немає.

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "lowercase")]
pub enum ScheduleType {
    Oneshot,
    Recurring,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct ScheduledRecording {
    pub id: String,
    pub stream_id: String,            // посилання на StreamInfo.id активного профілю
    pub name: String,                 // мітка користувача, напр. "Evening Jazz"
    #[serde(rename = "type")]
    pub schedule_type: ScheduleType,
    #[serde(default)]
    pub days: Vec<u8>,                // recurring: 0=Пн..6=Нд, непорожній; oneshot: порожній
    #[serde(default)]
    pub date: Option<String>,         // oneshot: ISO-дата "2026-06-14"; recurring: None
    pub time: String,                 // початок "HH:MM", 24h, локальний час
    pub duration_minutes: u32,        // 1..=1439; обчислюється з пари початок–кінець у формі
    pub enabled: bool,
    pub created_at: String,
    #[serde(default)]
    pub last_result: Option<ScheduleResult>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct ScheduleResult {
    pub occurrence: String,           // "2026-06-12T20:00" — номінальний локальний
                                      // час початку входження (без padding)
    pub status: ScheduleResultStatus,
    #[serde(default)]
    pub reason: Option<ScheduleResultReason>, // лише для Missed / StoppedByUser
    pub recorded_minutes: u32,        // wall-clock від фактичного старту до зупинки
                                      // (паузи реконектів не віднімаються); 0 — не стартував
    pub finished_at: String,          // ISO datetime, коли статус зафіксовано
}

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub enum ScheduleResultStatus {
    Completed,                // записано все вікно
    StartedLate,              // catch-up: стартували посеред вікна, дописали решту
    Missed,                   // вікно минуло без старту (Tapir не працював, DST-стрибок тощо)
    StoppedByUser,            // користувач зупинив плановий запис вручну
    SkippedAlreadyRecording,  // на старті вікна потік уже записувався
}

/// Код причини для Missed і StoppedByUser. Локалізує frontend (Paraglide, §5.6);
/// backend ніколи не віддає готові рядки.
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub enum ScheduleResultReason {
    // Missed:
    AppNotRunning,   // вікно минуло без жодної спроби старту в цій сесії
    StartFailed,     // спроби старту були, всі невдалі (потік недоступний, брак місця)
    ClockChange,     // неіснуючий локальний час (DST-стрибок уперед)
    // StoppedByUser:
    ManualStop,      // зупинка з UI або глобального хоткея
    ProfileSwitch,   // переключення профілю
    AppClosing,      // закриття додатка
    ScheduleEdited,  // редагування/вимкнення розкладу під час запису
}
```

Зміни відносно поточного scaffold: `day_of_week: Option<u8>` → `days: Vec<u8>`
(одна передача «пн–пт 18:00» = один розклад), додано `last_result`.
Синхронно оновити TS-типи й [docs/data-models.md](../../data-models.md) §3.3.

**Padding** — два поля в `RecordingSettings` профілю (не per-schedule):

```rust
#[serde(default)]
pub schedule_pad_before_min: u32,   // default 0
#[serde(default)]
pub schedule_pad_after_min: u32,    // default 0
```

Ефективне вікно запису: `start − padBefore … start + duration + padAfter`.
Межі 0–30 / 0–60 хв клампляться і на backend при збереженні налаштувань,
а не лише в UI (§5.4).

**Валідація** (на add/update і на load профілю):

- `recurring`: `days` непорожній, кожен елемент 0..=6, без дублікатів; `date = None`.
- `oneshot`: `days` порожній; `date` — валідна ISO-дата.
- `time` — валідний "HH:MM"; `duration_minutes` у межах `1..=1439`. Форма і так
  дає < 24 год (пара початок–кінець), верхня межа захищає від довільного
  `update_schedule`. У формі час кінця не може дорівнювати часу початку (запис
  на 0 або 24 години не підтримується). Padding може розтягнути вікно понад
  добу — це допустимо: вікна сусідніх днів одного розкладу перетнуться, і друге
  входження отримає `SkippedAlreadyRecording` (власність per-occurrence, §3.3);
  кінець першого вікна обробляє список активних входжень (§3.2, прохід A),
  а не пошук «найближчого вікна».
- `stream_id` існує в активному профілі (на add/update; на load — допускаємо «осиротілі»
  розклади, вони просто дають Missed з причиною в лозі).
- `oneshot` із вікном повністю в минулому — помилка валідації на add/update;
  `toggle_schedule(enabled = true)` для такого oneshot — та сама помилка
  (на load — допускається, дасть Missed і вимкнеться).
- Жорстко невалідний розклад на load (профіль — JSON на диску, його можуть
  редагувати руками) не валить завантаження профілю: елемент вимикається
  (`enabled = false`) із попередженням у лозі; рядок видно в таблиці,
  редагування через форму проходить повну валідацію і виправляє дані.
- `update_schedule` ігнорує `last_result` і `created_at` із клієнта — ці поля
  пише лише backend.

## 3. Ядро: `scheduler::timer`

Tokio-задача з `CancellationToken`, тік **щохвилини** (на початку кожної календарної
хвилини). Логіка **декларативна, за станом**, а не за подіями: на кожному тіку для
кожного enabled-розкладу активного профілю обчислюється «чи має зараз тривати запис?».
Модель самовідновлювана: сон системи, переведення годинника, редагування розкладів —
усе підхоплюється наступним тіком без спеціальної логіки.

### 3.1. Входження (occurrence) і ledger

Входження = конкретний запуск розкладу: ключ `(schedule.id, локальна дата+час початку)`.
In-memory ledger зберігає завершені входження поточної сесії
(`Completed | Missed | StoppedByUser | SkippedAlreadyRecording`). Призначення:

- **не перезапускати** запис у тому самому вікні після ручної зупинки;
- **гасити DST-повтор**: при переведенні годинника назад вікно збігається вдруге,
  але входження вже в ledger;
- не дублювати фіксацію Missed.

Ledger очищається від входжень, чиї вікна давно минули (досить тримати ~48 год).
Ledger не персиститься: рестарт Tapir посеред вікна після ручної зупинки призведе до
повторного старту через catch-up — прийнятне обмеження v1 (catch-up важливіший).

### 3.2. Алгоритм тіка

Scheduler веде in-memory список **активних входжень** — записів, які сам почав:
`(ключ входження, stream_id, session_id, window_end)`. `window_end` обчислюється
один раз у момент старту і зберігається як момент часу (instant/UTC), а не
перераховується з локального календаря щотіка — тому переведення годинника
назад під час запису не подовжує його на зайву годину. Кожна фіксація
результату (на тіку, при ручній зупинці, при shutdown) прибирає входження
зі списку активних.

Тік — два проходи.

**Прохід A — активні входження.** Для кожного входження зі списку:

- запис зник зі `StreamManager` (статусу немає) або `session_id` потоку вже
  інший (перезапущений користувачем) → прибрати зі списку **без фіксації**:
  входження не в ledger, тож прохід B перезапустить його в межах вікна
  (обрив ≠ скасування, §3.3);
- інакше, якщо `window_end` минув → зупинити запис, зафіксувати
  `Completed`/`StartedLate` + `recorded_minutes`, подія `scheduled-completed`,
  ledger. Завершення живе саме тут, а не в «найближчому вікні» проходу B:
  коли padding розтягує вікно понад добу (§2), найближчим вікном розкладу стає
  вже наступне входження — кінець попереднього інакше не був би оброблений
  ніколи, і запис не зупинився б.

**Прохід B — старти й Missed.** Для кожного enabled-розкладу активного профілю:

1. Обчислити найближче вікно `[start − padBefore, start + duration + padAfter)`,
   що накриває `now` або передує йому. Перехід через північ — природно через duration
   (вікно «23:00–01:00» належить дню старту). Обчислення мусить дивитись і на
   входження попередньої доби: вікно, що почалося вчора (через північ або через
   padBefore), може бути активним зараз. Пошук назад без штучного горизонту
   «24 години»: oneshot обчислюється з явної дати, recurring — найсвіжіший
   відповідний день тижня (до 7 діб назад). Інакше oneshot, чиє вікно минуло
   понад добу тому (Tapir довго не запускали), ніколи не отримав би Missed і
   завис би enabled назавжди — а §2 обіцяє «Missed і вимкнеться». Повторну
   фіксацію між сесіями гасить `last_result.occurrence` (крок 3).
2. **Вікно активне**, входження не в списку активних і не в ledger:
   - потік уже записується (вручну або іншим розкладом) → ledger:
     `SkippedAlreadyRecording`, оновити `last_result`. Skip фіксується один раз
     на вікно: навіть якщо конфліктний запис зупиниться посеред вікна, плановий
     уже не стартує — свідоме спрощення v1 (§8);
   - інакше → перевірка вільного місця (та сама `check_disk_space`, що в ручних
     командах старту, — scheduler не обходить її) і старт запису через
     `stream::manager`; входження додається в список активних із `session_id`
     (§3.3) та обчисленим `window_end`. Статус майбутнього результату —
     `StartedLate`, якщо хвилина тіка пізніша за `start` (номінальний початок,
     без padBefore; порівняння **з точністю до хвилини**: тік спрацьовує на
     мілісекунди пізніше рівної хвилини, тож порівняння повних моментів робило б
     StartedLate з кожного вчасного старту), інакше `Completed`; подія
     `scheduled-started`.
   - Помилка старту (потік недоступний, брак місця тощо) → нічого не фіксуємо:
     декларативна модель сама повторить спробу на наступному тіку, аж до кінця
     вікна. Факт «спроба старту була» запам'ятовується per-occurrence — від нього
     залежить причина майбутнього Missed (`StartFailed` vs `AppNotRunning`).
3. **Вікно щойно минуло**, входження не в списку активних (активні завершує
   прохід A) і не в ledger → `Missed` із кодом причини:
   `AppNotRunning` — у цій сесії не було жодної спроби старту (вікно минуло,
   поки Tapir не працював); `StartFailed` — спроби були, всі невдалі;
   `ClockChange` — DST-стрибок. Подія `scheduled-missed`, ledger, запис у лог.
   Дедуплікація між сесіями: якщо `last_result.occurrence` вже дорівнює цьому
   входженню — не фіксувати вдруге (ledger живе лише в пам'яті,
   а `last_result` персиститься).
4. Oneshot після фіксації результату (будь-якого) → `enabled = false`,
   рядок лишається в списку з результатом.
5. Кожна фіксація результату оновлює `last_result` і персистить профіль.

Чому «потік зайнятий» → skip, а «потік недоступний» → ретрай: у першому випадку
контент і так записується (користувач отримає аудіо), у другому — ні.

DST: неіснуючий локальний час (стрибок уперед) дає вікно, яке неможливо обчислити
на цю дату → фіксується `Missed (ClockChange)`.

### 3.3. Семантика власності

- Scheduler зупиняє **тільки** запис, який сам почав. `StreamManager` не знає,
  хто ініціював запис, тому власність трекає scheduler через **стабільний
  ідентифікатор сесії запису**. Зміна в `StreamManager`: `start_recording`
  присвоює `session_id: u64` (монотонний лічильник), кладе його в `StreamStatus`
  (+ синхронізувати TS-тип) і повертає викликачу; reconnect-цикл його не змінює.
  `recording_started_at` для власності непридатний: він `None` у стані
  Connecting і перезаписується на кожному успішному реконекті
  (`update_state_recording` всередині reconnect-циклу) — звірка по ньому
  вважала б запис «чужим» після першого ж обриву і ніколи не зупинила б його
  в кінці вікна. Scheduler запам'ятовує `session_id` свого входження; перед
  зупинкою в кінці вікна звіряє з поточним статусом — не збігається → запис
  чужий (перезапущений користувачем), не чіпати. Гонка довжиною ≤ 1 тік —
  прийнятна.
- Конфлікт на старті вікна (потік уже пишеться) → skip, нічого не чіпаємо в кінці вікна.
- **Ручна зупинка vs фатальний обрив — розрізняти в точці зупинки, не на тіку.**
  `StoppedByUser (ManualStop)` фіксується в момент ручної зупинки, якщо потік
  належить scheduler-сесії (звірка за `session_id`) → ledger, у цьому вікні не
  перезапускати. **Шляхів ручної зупинки чотири**, фіксація потрібна в кожному:
  команда `stop_recording` (кнопка потоку), команда `stop_all_recordings`
  (кнопка «Зупинити все»), глобальний хоткей toggle-recording і глобальний
  stop-all (`recording_control::{toggle_all, stop_all_now}`). Інакше «Зупинити
  все» перезапускалося б scheduler-ом уже наступного тіка. Реалізація — спільний
  хук `scheduler::notify_manual_stop(stream_id, session_id)` у цих точках:
  викликач читає `session_id` зі статусу потоку **до** скасування токена
  (після cancel запис зникає з manager асинхронно — звіряти було б ні з чим);
  stop-all-шляхи викликають хук для кожного активного потоку. Scheduler фіксує
  `StoppedByUser`, лише якщо переданий `session_id` збігається зі збереженим у
  його активного входження; інакше хук ігнорується — зупинили ручний запис,
  що зайняв потік (напр., після обриву планового), і catch-up у вікні має
  лишитися можливим.
  Якщо ж запис зник сам (reconnect вичерпано, задача впала) — входження НЕ в ledger,
  і наступний тік перезапустить запис у межах вікна. Це бажано: обрив ≠ скасування.
- `remove_stream` теж зупиняє активний запис потоку; окремої обробки не треба:
  розклад стає осиротілим, спроби старту падають → `Missed (StartFailed)`
  у кінці вікна.
- Два розклади перетнулись на одному потоці → другий отримує `SkippedAlreadyRecording`.
- Обрив з'єднання під час планового запису → діє існуюча reconnect-логіка
  (Settings → Reconnection); scheduler не втручається, вікно закривається за часом.

### 3.4. Пайплайн запису

Плановий запис використовує **стандартний пайплайн Фази 1** без змін: розділення
треків, wishlist/ignorelist, шаблони імен файлів, stream file — усе за поточними
`RecordingSettings` профілю. Безперервний файл передачі дає існуюча опція
`saveStreamFile`. Кілька розкладів на різних потоках пишуться паралельно
(`StreamManager` це вже підтримує). Іменування за назвою розкладу — backlog (§1).

### 3.5. Життєвий цикл задачі

- Старт задачі — після завантаження активного профілю **і ready-сигналу
  frontend**; перший тік — на початку наступної календарної хвилини. Інакше
  catch-up першого тіка може емітити `scheduled-started` до того, як webview
  підписався на події, — втрачене озвучення.
- Під час активного запису система не засинає — існуючий `WakeLock`
  (`SetThreadExecutionState`) уже тримає її. Тобто сон ОС загрожує лише **старту**
  запланованого запису, а не його продовженню.
- Переключення профілю: confirm dialog, якщо триває плановий запис
  («Триває плановий запис "X" до 22:05. Переключити профіль і зупинити його?»;
  якщо активних кілька — перелік і множина в тексті);
  при підтвердженні — зупинка (статус `StoppedByUser (ProfileSwitch)`),
  ledger, список активних входжень і таймер перезапускаються на нових розкладах.
- Закриття додатка під час планового запису → той самий confirm; graceful shutdown
  зупиняє запис штатно, фіксується `StoppedByUser (AppClosing)`. Після
  рестарту catch-up все одно дозапише залишок вікна як `StartedLate`: `last_result`
  блокує лише повторну фіксацію Missed, а не старт запису (старт блокує тільки
  in-memory ledger).
- **Планові записи не потрапляють в `active_recording_urls`** при shutdown.
  Інакше після рестарту запис відновився б як «ручний» (нічийний): scheduler
  побачив би зайнятий потік → Skipped, і в кінці вікна ніхто б його не зупинив —
  запис тривав би вічно. Відновлення планових записів — виключно через catch-up.
  Фільтр у `graceful_shutdown` — за `session_id` scheduler-owned записів;
  `session_id` зчитуються зі статусів **до** `stop_all()` — після скасування
  записи зникають з manager асинхронно.
- Редагування розкладу, що зараз пише: зупиняти запис **лише якщо змінились
  суттєві поля** (`stream_id`, `time`, `days`, `date`, `duration_minutes`) —
  зміна назви запис не перериває (інакше перейменування розривало б файл і
  давало рестарт через тік). Зупинене входження фіксується як
  `StoppedByUser (ScheduleEdited)` + `recorded_minutes`, подія
  `scheduled-completed`, ledger під старим ключем входження; далі — за новим
  станом на наступному тіку. Вимкнення (toggle off) — та сама фіксація і ledger
  (повторне увімкнення в тому ж вікні не рестартує). Видалення — просто зупинка
  (фіксувати нікуди, рядок зник).
- Увімкнення (або створення) розкладу посеред уже активного вікна → запис почнеться
  на наступному тіку як catch-up (`StartedLate`). Це очікувана поведінка.

## 4. IPC

Модуль `commands/schedule_commands`:

| Команда | Сигнатура (вхід → вихід) |
|---------|--------------------------|
| `get_schedules` | `() → Vec<ScheduleDto>` — `ScheduledRecording` + обчислене `nextRun: Option<String>` |
| `add_schedule` | `(ScheduledRecordingInput) → ScheduledRecording` (id, createdAt генерує backend) |
| `update_schedule` | `(ScheduledRecording) → ScheduledRecording` |
| `delete_schedule` | `(id: String) → ()` |
| `toggle_schedule` | `(id: String, enabled: bool) → ScheduledRecording` |

Усі команди працюють з активним профілем і одразу персистять його. Помилки — через
`RadioError`.

Обчислення вікон і наступного запуску живе **тільки в Rust** — frontend не дублює
календарну логіку. `nextRun` — ISO локальний datetime `"YYYY-MM-DDTHH:MM"`
(той самий формат, що `ScheduleResult.occurrence`), **не** display-рядок:
frontend лише форматує його для показу (день тижня, локаль — §5.6); інакше
backend мусив би локалізувати назви днів, порушуючи правило «backend не
віддає готових рядків».

Події: `scheduled-started`, `scheduled-completed`, `scheduled-missed`,
`scheduled-skipped`. Розширені payload відносно data-models.md (оновити §6 там
само) — live region має озвучувати подію одразу, без рефетчу:

- усі чотири: `recordingId` (= `ScheduledRecording.id`), `streamId`, `name`;
- `scheduled-completed`: + `status` (Completed | StartedLate | StoppedByUser),
  `recordedMinutes`;
- `scheduled-missed`: + `reason` — **код** `ScheduleResultReason`, локалізує
  frontend (§5.6), backend не віддає готових рядків;
- `scheduled-skipped` — емітується при `SkippedAlreadyRecording`: без неї панель
  не оновила б `last_result`, а NVDA-користувач не дізнався б, що плановий
  запис не стартував.

`scheduled-completed` емітується і в момент фіксації `StoppedByUser` (не лише в
кінці вікна) — інакше панель не оновить результат. Frontend для `StoppedByUser`
лише оновлює store, без announce: ручну зупинку вже озвучує існуючий
recording-флоу, дублювати не треба.

Поточний стан самого запису йде через існуючі recording-статуси по `streamId` —
нових механізмів статусу не потрібно.

Frontend store: `src/stores/schedule.ts` (nanostores) — список розкладів;
оновлюється викликом `get_schedules` при відкритті панелі та після кожної
події `scheduled-*` (вони ж сигналізують зміну `last_result`/`enabled`/`nextRun`).

## 7. Тестування

**Unit (Rust, `scheduler::timer` — чиста логіка обчислення вікон окремо від tokio):**

- Найближче вікно: recurring у різні дні, oneshot, перехід через північ, padding;
  вікно, що почалося попередньої доби (через північ або padBefore), активне «сьогодні».
- Вікно понад добу (duration + padding > 1440 хв): прохід A зупиняє перше
  входження за збереженим `window_end`, друге входження →
  SkippedAlreadyRecording.
- Catch-up: now посеред вікна → старт StartedLate; now після вікна → Missed;
  старт точно в хвилину `start` (без padding) → Completed, не StartedLate
  (хвилинна гранулярність порівняння).
- Ledger: повторний тік не дублює старт; StoppedByUser не перезапускається;
  DST назад не дає другого старту і не подовжує активний запис
  (`window_end` — instant); DST уперед дає Missed.
- Невдалий старт → ретрай наступного тіка; вікно вичерпано без старту → Missed.
- Власність: `session_id` не збігається → чужий запис не зупиняється в кінці
  вікна; свій `session_id` стабільний через reconnect → запис зупиняється;
  фатальний обрив (зник без stop-команди) → перезапуск у вікні.
- Ручні зупинки: `notify_manual_stop` із будь-якого шляху (stop, stop-all,
  глобальні хоткеї) → StoppedByUser у ledger, без рестарту в тому ж вікні;
  хук із `session_id`, що не збігається (зупинено ручний запис, який зайняв
  потік після обриву планового), → ігнорується, StoppedByUser не фіксується,
  рестарт у вікні лишається можливим.
- Oneshot із вікном, що минуло понад добу тому, на load → Missed (AppNotRunning),
  `enabled = false`.
- Причина Missed: без спроб старту → AppNotRunning; зі спробами → StartFailed.
- Валідація моделі (days, date, time, duration `1..=1439`, кінець ≠ початку,
  toggle-enable відпрацьованого oneshot → помилка); жорстко невалідний розклад
  на load → `enabled = false` + лог, профіль завантажується.

**Ручний сценарій (з NVDA):**

1. Розклад на now+2 хв, тривалість 2 хв → стартує, озвучується, зупиняється, файл є,
   last_result «✓».
2. Закрити Tapir до старту, відкрити посеред вікна → StartedLate, дописано решту.
3. Зупинити плановий запис вручну → не рестартує, статус «зупинено вручну».
4. Запустити ручний запис потоку, дочекатись планового старту → skip, ручний запис
   не зупинено в кінці вікна.
5. Переключити профіль під час планового запису → confirm, запис зупинено.
6. Закрити Tapir під час планового запису, відкрити знову (вікно ще активне) →
   запис відновлюється один раз через catch-up (StartedLate), без дубля від
   `active_recording_urls`.
7. Глобальний stop-all (хоткей) під час планового запису → зупинено, статус
   «зупинено вручну», без рестарту до кінця вікна.
8. Обірвати мережу під час планового запису, дочекатися реконекту, дочекатися
   кінця вікна → запис зупинено штатно (session_id пережив reconnect).

## 8. Рішення, прийняті на brainstorming (для історії)

| Питання | Рішення |
|---------|---------|
| Гарантія спрацювання v1 | Tapir має бути запущений; wake-from-sleep і Task Scheduler — backlog |
| Повторюваність | Набір днів тижня (`days: Vec<u8>`) замість одного `dayOfWeek` |
| Надолуження | Старт із запізненням, якщо вікно ще активне (StartedLate) |
| Форма часу | Початок + кінець; кінець < початку = через північ (рівність — помилка); зберігаємо duration |
| Padding | Глобальне налаштування (профіль), per-schedule override — backlog |
| Oneshot після спрацювання | enabled=false, рядок лишається з результатом |
| Профілі | Розклади лише активного профілю; переключення з активним записом — confirm dialog |
| Ядро | Per-minute tick loop, декларативна перевірка стану + ledger входжень |
| Конфлікт на старті вікна | Skip фіксується раз на вікно; рання зупинка конфліктного запису планового старту не повертає (свідоме спрощення v1) |
