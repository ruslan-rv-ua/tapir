# Уніфіковане контекстне меню для composite-списків

**Дата:** 2026-06-07
**Статус:** Затверджено (дизайн), готово до планування реалізації

## Проблема

У списку потоків (і, як з'ясувалося, в усіх composite-списках):

1. **Клавіша Menu / Shift+F10:** з'являється контекстне меню застосунку, але **разом із ним** — дефолтне меню браузера (WebView2). Два меню одночасно.
2. **Правий клік миші по рядку:** з'являється **лише** дефолтне меню браузера; меню застосунку не відкривається.

## Корінь проблеми (єдиний для обох багів)

Жоден список не обробляє DOM-подію `contextmenu`. Контекстне меню відкривається виключно через `keydown`:

- `useCompositeList` на клавішах `ContextMenu`/`Shift+F10` диспатчить екшен `contextMenu`
  (`src/hooks/useCompositeList.ts:332-341`);
- `onAction` кожного списку знаходить кнопку `[data-context-menu-trigger]` і робить `.click()`
  (`src/components/streams/StreamList.tsx:90-95` та аналогічно в Songs/Profiles).

Наслідки:

- **Баг 1:** `preventDefault()` на `keydown` **не скасовує** окрему подію `contextmenu`, яку
  WebView2 генерує після натискання клавіші Menu. Меню застосунку відкривається з keydown,
  а меню браузера — з непригніченої події `contextmenu`.
- **Баг 2:** події `contextmenu` від миші ніхто не слухає, тож меню застосунку не відкривається —
  лишається лише нативне меню WebView2.

Обидва баги відтворюються **в усіх трьох списках** (Streams, Songs, Profiles), бо вони
використовують спільну механіку `CompositeList` + `useCompositeList` з ідентичним патерном.
Тому виправлення належить **спільному шару**, а не трьом місцям.

## Рішення: подія `contextmenu` як єдине джерело істини

Chromium/WebView2 емітить DOM-подію `contextmenu` для **усіх трьох** тригерів: правий клік миші,
клавіша Menu, Shift+F10. Це дозволяє звести обробку до одного шляху.

### Прийняті рішення (з брейнштормінгу)

- **Розташування меню при правому кліку:** прив'язане до кнопки ⋯ того ж рядка
  (повторно використовуємо наявний шлях відкриття, консистентно з клавіатурою).
- **Фокус при кліку по неактивному рядку:** спершу робимо рядок активним (roving focus → `summary`),
  потім відкриваємо меню. Після закриття фокус повертається логічно.
- **Охоплення гасіння нативного меню:** лише в межах списків (`role="application"` контейнери `<ul>`).
  Усередині них немає виділюваного тексту чи полів вводу, тож нативне меню там нічого не дає.
  Глобальне гасіння (крім полів вводу) — окремий follow-up, поза цим багфіксом.

## Архітектура

Уся логіка переноситься у спільний шар (`useCompositeList` + `CompositeList`). Три списки лише
втрачають дубльований код.

### 1. `useCompositeList` — новий обробник `onContextMenu`

Повертається з хука разом із `onKeyDownCapture`. Логіка:

1. `e.preventDefault()` **завжди** → гасить дефолтне меню WebView2 в межах списку (і для миші,
   і для клавіатурних тригерів).
2. Резолв рядка: `(e.target as HTMLElement).closest('[data-item-id]')`.
   Якщо рядка немає (правий клік по порожній зоні списку чи футеру) — лише `preventDefault`,
   нічого не відкриваємо.
3. Якщо `itemId` присутній у `items` → робимо рядок активним (фокус спершу на рядок) **без**
   програмного `pendingFocus`, і клікаємо `[data-item-id=…][data-context-menu-trigger]`
   всередині `listRef`.

**Критична деталь реалізації:** активний рядок оновлюємо станом, але DOM-фокус **не** смикаємо
вручну (не використовуємо `pendingFocusRef`). Далі фокусом усередині відкритого меню володіє
React Aria. Інакше `useLayoutEffect` хука з `pendingFocusRef` конкурував би з React Aria за
фокус і ламав би щойно відкрите меню. Для цього потрібен варіант оновлення активної позиції,
який змінює `activeItemId`/`activeSegment` без черги програмного фокуса.

### 2. `CompositeList`

Вішаємо `onContextMenu={onContextMenu}` на `<ul>` (`src/components/common/composite-list/CompositeList.tsx:108-115`).

### 3. Прибирання старого

- Видаляємо `case 'ContextMenu'` і `case 'F10'` (Shift+F10) з `keydown`
  (`src/hooks/useCompositeList.ts:332-341`) — саме вони спричиняли подвійне меню.
- Прибираємо `'contextMenu'` зі `ActionType` (`src/hooks/useCompositeList.ts:31`).
- Видаляємо однакові гілки `if (type === "contextMenu") { menuBtn.click() }` у:
  - `src/components/streams/StreamList.tsx:90-95`
  - `src/components/songs/SongsList.tsx:38-44`
  - `src/components/profile/ProfileList.tsx:49-55`

## Потік даних (єдиний для всіх входів)

```
правий клік / Menu / Shift+F10
  → подія `contextmenu` на <ul>
  → preventDefault()  (гасить нативне меню WebView2)
  → резолв рядка через closest('[data-item-id]')
  → активувати рядок (без програмного фокуса)
  → клік по [data-context-menu-trigger] рядка
  → React Aria відкриває Popover/Menu
  → (після закриття) React Aria повертає фокус на ⋯
```

Поведінка після закриття меню ідентична поточному клавіатурному шляху — без регресу.

## Тестування

`src/hooks/useCompositeList.test.tsx`:

- Замінюємо keydown-перевірки `ContextMenu`/`Shift+F10` (рядки 245-263) на dispatch події
  `contextmenu`. У Harness додаємо в рядок елемент із `data-context-menu-trigger`.
- Перевіряємо:
  - `preventDefault` викликано на події `contextmenu`;
  - тригер активного рядка клікнуто;
  - правий клік по **неактивному** рядку переносить активність на нього перед відкриттям;
  - правий клік по порожній зоні списку лише гасить меню (тригер не клікнуто).
- «Bare F10 нічого не робить» лишається (тепер тривіально — події `contextmenu` немає).

## Верифікація вживу (Tauri / WebView2)

Ручна перевірка в реальному застосунку — це суть багу, тож обов'язкова:

- клавіша Menu і Shift+F10 емітять `contextmenu`, і `preventDefault` гасить нативне меню;
- правий клік відкриває меню застосунку біля кнопки ⋯;
- немає подвійного меню при клавіші Menu;
- перевірити в усіх трьох списках: Streams, Songs, Profiles.

## Крайові випадки

- Правий клік по порожній зоні списку / футеру («Load more») → нативне меню погашено, нічого не
  відкривається.
- Поза списками (діалоги, поля вводу) нативне меню WebView2 лишається — свідомо, окремий follow-up.
- Bare F10 (без Shift) → події `contextmenu` немає → нічого (узгоджено з поточним наміром).
